## 4. 調査で分かったこと(原因)

- **撤退から戻ると飛ぶ**: 戻った日の処理が、戻っただけで終わらなかった(§2-1)。初期パーティ1つだけで再現した(そのシナリオに限らず、どのシナリオでも起きる。デフォルトのシナリオでも再現した)。
- **会話の時点で既に撤退している**: 勝てない相手は、判定が失敗するだけで戦闘は行われず、会話が開く。ところが同じ日のうちに`_check_blocked`が走り、会話の表示中に退避が確定していた。実際に戦って負ける場合は、HP・休養が会話の前に適用されていた。
- **アイコンが最後のフロアへ**: §2-4。次のセクションは、フロアが1つも発見・突破されていないので、どの優先順にも当たらなかった。
- **Androidで1人しか選べない**: 編成が`ItemList`の複数選択(`SELECT_MULTI`)で、Ctrl/Shift前提。タッチの1タップは選択を置き換える。さらに、既存パーティに追加する機能が、Androidに限らず、最初から無かった(解散は、以前からある)。
- **雇用上限と拡張**: 上限は名簿の総人数(初期パーティ4人を含む)で数え、初期5・拡張+2だった。パーティ(4人)と噛み合わず、端数が出た。
- **難度(個人用のテストシナリオ)**: 強化なしの初期パーティで、最初の作品の本編6セクションに約276日(デフォルトの王国は、6セクションで約90日が目標)。ログウィンドウで見ると、多くの日を「力を付けている」で過ごしている。**ユーザーには報告したが、まだ調整していない**。

## 5. 手法と落とし穴(次にやる人向け)

- **`--script`のシミュレーション**: 毎日、開いた会話を最後まで進める(`EventDialogue`の`advance()`/`choose(0)`)。開いたままだと、その間は他のフロアの発見が全て見送られ、シナリオが壊れているように見える(3000日発見ゼロ)。前のスロットの開いた会話が、次の`create_new_slot`にも残る。必ず隔離した`APPDATA`(`tools/dev/README.md`)。
- **`:=`は、型なしのautoload変数から得た値に使えない**(パース時にスクリプト全体が読めなくなる)。`var x: Array = ...`と明示する。
- **`RichTextLabel.append_text`はBBCodeを解釈する**。任意の文字を出す時は`add_text`/`push_color`。
- **見た目の確認**: ヘッドレスは描画しない。`--headless`を付けずに`godot --path godot --resolution 1152x648 --script <スクリプト>`を隔離`APPDATA`で流し、スクリプトの中で`get_viewport().get_texture().get_image().save_png()`。タッチUIは`-- --touch-ui`(と`--resolution 1600x720`)。数秒だけウィンドウが出る。複数画像を1枚にまとめる時は、`Image.blit_rect`の前に、形式をそろえる(`convert(RGBA8)`)。新しい`class_name`は、`--import`で登録する。
- **チェックボックスのタップのシミュレーション**: `button_pressed = true`で`toggled`が出る。
- **定期更新するUIは、中身が同じなら作り直さない**(パーティ画面は日ごとに更新。作り直すと、押している最中にノードが消えてタップが取りこぼされる)。
- **コミットの分割**(対話的な`git add -p`が使えない環境): 混在するファイルは、系統ごとのテキストを作り、`git hash-object -w --path=<file>`+`git update-index --cacheinfo`でステージ。大きなファイルは、`git diff -U3`を`@@`で分け、キーワードで分類し(**分類は目で確認する**。キーワードの誤反応があった)、選んだハンクを`git apply --cached --recount`。各コミットの前に、`git checkout-index -a --prefix=<一時>/`で展開して、コンパイルとシミュレーションを流す。
- **ツール層**: 長い日本語のPythonをbashのヒアドキュメントに入れると壊れる(今回も再発)。パッチのスクリプトは`Write`でファイルにして実行する。`\n`は`chr(92)`で組み立てる。
- **WebFetchの要約は当てにならない**(存在しないボス名を作った)。事実は、生のHTMLをcurlで取って確かめる(日本語版Wikipediaのrest_v1 API。UAを名乗る)。

**進め方の作法**(このユーザーの好み。メモリにもある)
- 遊んだ後の報告は、短く、観察の形で来る(「〜になってしまう」)。**まず再現して原因を特定**し、設計の選択がある時だけ質問する。「まず現状を確認する」と言われたら、調べて報告してから案を出す。
- 提案が目的に合っていなければ、ユーザーは理由を添えて却下する(「入れ替わるのでは表示しないのと同じでは?」)。数字や運用(見返しの期間など)で、提案の穴を先に埋める。
- 質問は日本語、選択肢は推奨を先頭に「(推奨)」、見た目が絡む時はASCIIのプレビューを付ける。今回は、ほぼ全て推奨が選ばれた。
- 実装したら、ゲーム本体で確認(隔離`APPDATA`のシミュレーションと、必要なら実ウィンドウの画像)してから報告する。
- **コミットは、ユーザーが「コミットして下さい」(または、コミットの分け方の提案に「はい」)と言ってから**。テーマごとに分ける(今回は、探索の順序 / 探索者一覧+会話 / ログ / アイコン / タイムバー / 雇用上限とパーティ)。ステージした状態そのものを、別の場所に展開して検証してからコミットする。
- ファイルの書き換えは、`Edit`ツールか、バイナリモードのスクリプト。長い日本語を含むパッチは`Write`でファイルにする。
