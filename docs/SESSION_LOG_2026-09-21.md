## 4. 調査で分かったこと(原因)

- 既存の`world_schema_db.gd`(内容ハッシュ版管理、スロットが自分のバージョンを記録)は、「シナリオのスナップショット」にそのまま拡張できた。会話をスナップショットに含めたことで、**エディタで直しても、既存スロットは遊び始めた時点の内容のまま**になる(設計の利点であり、「エディタで直したのにゲームで変わらない」と思われやすい点)。
- ゲームは、フロアの会話の**終わりの結果コード(`pass`)で突破を確定する**(`_finalize_discovery(outcome == "pass")`)。フロアの会話が`pass`/`fail`で終わらないと、突破が確定しない。エディタの検証で検出する。
- ゲームのデータは全ての行に`next: i+1`を明示していた。行の挿入・並べ替えで「一覧の並び=会話の流れ」を保つには、編集前に、これを省略に直す必要があった。
- 案内会話の導入・前編は、起動直後にしか流れなかった。起動直後は常にデフォルトシナリオなので、自作の導入が出なかった(ユーザーの指摘の後に修正)。
- Androidでも`DirAccess.open("res://scenarios")`の一覧が機能した(懸念していたが、起動ログで確認)。

**設計判断**(ユーザーに聞かず、こちらで決めた。理由は`scenario_editor.md`)
- 編集は「下書き」(保存済みの世界の複製。各要素に`_orig`=保存済みのときのID)に対して行い、保存でまとめて書く。`_orig`があるので、ID変更・削除の、保存済みイベントへの波及を、保存時に正しく求められる(AとBの入れ替えも)。
- **接続は常に双方向で保存**: ゲームは「発見されるフロア自身の接続」に突破済みの隣があるかで発見を決める(`WorldMap.frontier_for_section`)ため、片方向は一方通行になる。
- **削除は、参照するイベントを消さない**(確認に一覧を出し、保存後の検証でエラーに)。条件を勝手に消すと発生の意味が変わるため。
- 保存を止めるのは`fatal`(ID違反・重複、存在しない所属・接続先、不正なゲート)だけ。それ以外(片方向の接続、到達不能、未定義のアイテムなど)は警告・エラーとして表示するが保存はできる(手書きの不完全な`world.json`を、エディタで少しずつ直せるように)。

**調べて分かったこと**
- **フロアの並び=ゲームのマップ画面の配置**: ゲームは座標を持たず、セクション内のフロアを配列順に5列(`MAP_COLUMNS`)で折り返して並べる(`main.gd`の`_compute_node_positions`)。だから、フロアの並べ替え(◀▶)が要り、セクションのフォームに格子で出している。エリアの並び=収入・報酬の倍率(`section_multiplier`)、セクションの並び=退避先の判定(`previous_cleared_section`)。
