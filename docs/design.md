# ローグライク自動探索 設計ドキュメント

## 1. コンセプト

**世界観**: 中世ファンタジー。魔法・遺跡・血筋・リドルといった要素が自然に馴染む舞台とする。

**ゴール設計**: 明確な終了条件は設けない**エンドレス型**。スタークラフター系インクリメンタルゲームのように、雇用の拡大と探索者の育成を継続的に楽しむことを主眼とする（「クリア」を目的としない）。

OpenWorld的なマップを、技能を割り振った探索者に探索させる放置系ゲーム。
プレイヤー自身が直接操作するキャラクターはいない（方針指定のみ）。プレイヤーは複数の探索者を雇用し、探索方針（鍛えるスキル・担当エリアなど）を指定するだけで、実際の移動・判定はすべて自動で進行する。

新しく見つかった道や発見は、常設の内部掲示板に記録される。イベントの規模によっては即時に表示され、それ以外は月次の集計タイムでまとめて報告される。

## 2. コアループ

**初期状態(2026-09-14実装済み)**: ゲーム開始時、プレイヤーには最初から4人構成のパーティが1つ、購入・募集不要で用意されている（得意スキルが偏らないよう構成済み、装備は最下級の「木」等級、血筋は平民中心。詳細は4.7節）。募集・雇用（4.4節）は、2つ目以降のパーティを編成するための拡張手段として引き続き存在する。（旧仕様: 雇用探索者0人スタートで、最初の募集・雇用自体がチュートリアルを兼ねる形だった。パーティ制導入によりこの初手の位置づけを変更する）

1. 探索者を雇用する（募集をかけ、提示された候補から選ぶ）
2. 雇用した探索者に探索方針・担当エリアを指定する
3. 時間が進行し、探索者が自動で探索・判定を行う
4. 発見や成果が掲示板に記録される（一部は即時、大半は月次）
5. 月末に集計タイムで結果が表示され、時間が一時停止する
6. プレイヤーが内容を確認し、方針を調整してから次の月へ進める（プレイヤーの確認操作が必要）
7. 得た利益（アイテム・資金）を「新規雇用（拡大）」と「既存探索者のスキル強化」に配分する

このサイクルを繰り返しながら、マップの探索範囲・探索者の練度・雇用規模を広げていく。

## 3. 時間システム

- **基準ペース**: 1ヶ月（30日）＝ 実時間25分（等速=1x）。ポモドーロ・テクニックの1セッション分に相当し、「探索者に方針を指定してタイマーを走らせ、他の作業をしながら待つ」という遊び方を想定する
- **倍速機能**: 1x/10x/100x/1000xの段階式（2026-09-13〜、指数的に伸びる方が体感の伸びが分かりやすいとして1x/2x/4x/8x/16xから変更）。UIは1ボタンの順送りクリックではなく、全段階を横に並べたボタン列から直接選ぶ方式（2026-09-13〜）。制限は設けない（戦闘中でも自由に変更できる）。最大1000xで1ヶ月あたり約1.5秒まで短縮できる
- 月末までの残り時間は、控えめな表示（小さなラベルでmm:ss表示）で画面に常設する。ポモドーロ的な巨大なカウントダウン演出はしない
- **暦表示**: カウントダウンとは別に「0年1月1日」のような年月日も常設表示する。暦の起点（開始年月）はデフォルト0年1月だが、`TimeSystem.start_year`/`start_month`として保持しており、将来シナリオ選択機能ができた際にプレイ開始時の年月を差し替えられるようにしてある（現時点ではシナリオ機能自体は未実装で、常にデフォルト値が使われる）
- **セッション型**: ゲームを起動している間だけ時間が進行する。終了している間は進行しない（サーバー側での常時稼働はしない）
- 月末になると自動的に時間が停止し、月次サマリを表示する
- **時間進行の計算方式(2026-09-13、フレームdelta蓄積方式から書き直し)**: 当初は`_process(delta)`のフレームdelta(Godotの計測値)を毎フレーム`_accumulated`に足し込み、閾値(1日分の秒数)を超えた分だけ`while`ループで一気に`_advance_day()`する方式だった。これは「フレームのdeltaが実際の経過時間を正しく反映している」という前提に依存しており、重い`_ready()`直後や`--headless --quit`のような短命プロセスでその前提が崩れると、1フレームで何日分もの`_advance_day()`が連続実行され、日付が瞬時に飛んでしまう不具合があった(初回フレームのdeltaだけを捨てる対策を一度入れたが、それでも起動チェックを繰り返すだけで日付がドリフトする事象が残り、不十分と判明)。**根本的に、Godotのフレームdeltaを信用せず、`Time.get_ticks_msec()`による実時間タイムスタンプの差分から経過時間を計算する方式に書き直した。** さらに、1回のチェックで進められる日数を最大1日に制限し(`if _accumulated >= SECONDS_PER_DAY`、以前は`while`)、それを超える分(遅延)は`_accumulated`に残したまま次回以降のチェックで段階的に追い上げる方式にした(「日付を瞬時に大きく飛ばして帳尻を合わせるより、多少遅延しても後から徐々に追いつく方が良い」という方針)。起動時の基準リセット(`TimeSystem.mark_boot_complete()`)を`main.gd`の`_ready()`の一番最後(UI構築・セーブロードなど重い処理が全て終わった直後)に明示的に呼ぶことで、起動処理にかかった実時間そのものを経過時間の計算から除外している。`--headless --quit`を5回連続で実行しても日付が一切進まないこと、および人為的に60秒分のギャップを与えても1チェックにつき1日しか進まず残りが正しく繰り越されることをテスト用の直接呼び出しで確認済み
- 次の月への移行は自動再開ではなく、プレイヤーの確認操作によって行う（ターン制に近い区切り）

## 4. 探索者

**用語(2026-09-20決定)**: プレイヤーが雇って探索に送り出すキャラクター(雇用・野良の両方)を「**探索者**」と呼ぶ。以前は「NPC」と呼んでいたが、町人やイベントに登場するキャラ用の画像(`npc_01`〜`npc_32`)を用意したため、一般的な意味での「NPC」(町の人・イベントキャラ)と紛らわしくなった。今後「NPC」は町人・イベントキャラのために空けておく(画面上は「住人」や、名前と役割で呼ぶ)。素材の命名(探索者=`char_`、町人=`npc_`、敵=`enemy_`)もこの区分に一致している。**コード上の識別子(`npcs.gd`・`Npcs`・`npc_id`・DBの`npcs`/`npc_skills`等のテーブル名)は改名していない**(セーブの移行が必要なため。画面の文字・設計書・コメントだけを変更した)。コード中の`npc`は「探索者」を指す。

### 4.1 種別

- **雇用探索者**: プレイヤーと雇用関係にあり、方針指定に従って探索する。利益・成果はプレイヤーに還元される
- **野良探索者**: 誰にも雇われず、世界の中で勝手に探索しているAI制御の探索者。プレイヤーの利益には直結しないが、発見自体は世界共通の情報として掲示板に反映される（後述）。雇用探索者と**同じワールドの実データ（found/passed）を実際に探索する**存在（フレーバー演出ではない）
  - **できること/できないこと**: ゲートのないフロアは雇用探索者と同様に発見・通過できるが、スキル判定や戦闘が必要なゲートは突破できない（「発見済みだが進めない」状態で見つけるだけに留まる）。実際のゲート突破は雇用探索者の役目
  - **母数**: セクションごとに一定確率で発見が発生する形でシミュレートし、「世界が常に動いている」感覚を演出する
  - **雇用探索者との関係**: 野良探索者が将来雇用候補として現れることはない。**完全に別の存在・別ロジック**として扱い、雇用候補生成システムとは切り離す

### 4.2 先天的特性（血筋・種族など）

血筋・種族のような属性は、後天的に鍛えられる「スキル」とは別枠で扱う**生まれつきの固定パラメータ**。雇用時（候補提示時）に決定され、訓練では変更できない。特定の血筋でしか開かない場所を作ることで、雇用選択にコレクション性・戦略性を持たせる。

**肖像画像(2026-09-14実装済み)**: 探索者管理パネルのロースターカード・詳細ビューにこれまで表示していた「血筋色の正方形+頭文字」のプレースホルダを、実際の肖像画像に差し替えた。ユーザーが用意した生成済み画像40枚(`sandbox/charactors/`)を`godot/assets/portraits/`に配置し、`portrait_library.gd`(`class_name PortraitLibrary`)が`NameGenerator`と全く同じ「血筋別プールからの抽選」パターンで、雇用時に探索者へ1枚割り当てる(`npcs.gd`の`hire()`)。40枚のうち人型でない3枚(骸骨/リッチ、ゴーレム、狼単体の動物)は通常の探索者として不自然なため抽選対象から除外し(ファイル自体は残置、将来モンスター表示等に転用可能)、残り37枚を絵柄の雰囲気(エルフ耳→森人の血、王冠/王族衣装→王家の落胤、貴族風衣装→旧家の血筋、それ以外の人間・亜人・モンスター種族→平民)で振り分けた。オーク・ドワーフ・獣人・悪魔・竜人・人魚などの非人間種の絵柄はどの血筋にも明確な一致が無いため平民プールに含めている(平民は「特別な血筋を持たない」という消極的な定義のため、多様な種族の受け皿として矛盾しない)。旧セーブ(肖像未割り当て)は次回ロード時に自動で抽選・付与される(job/unique_skillの移行と同じ方式)。画像が万一見つからない場合は従来のプレースホルダ表示にフォールバックする。

**肖像画像の差し替え(2026-09-19)**: 縦長の40枚を、ユーザーが正方形に作り直した48枚(`char_01`〜`char_48`)に差し替えた。元画像は番号付きの一覧シートの切り出しで、縁の白枠と左上の番号が焼き込まれていたため、`tools/prepare_portraits.py`で縁と番号を取り除き、256x256にして`godot/assets/portraits/`へ出力する(画像を差し替える時は必ずこのスクリプトを通す)。画像はOpenAIの画像生成サービスで著者が生成したもので、利用条件は`godot/licenses/LICENSE-IMAGES.md`にあり、ゲーム内の左メニュー「ライセンス」からも読める(音楽などを追加する時の手順は`docs/HANDOFF.md`の「ライセンス画面」)。除外は人型でない/顔の見えない3枚(`char_16`ゴーレム、`char_24`骸骨、`char_32`顔の見えない黒騎士)、残り45枚を血筋へ振り分け直した(平民30・旧家5・森人6・王家4、`portrait_library.gd`)。ファイル名が同じで中身が変わったため、旧セーブの探索者は名前・血筋そのままで別の顔になる(壊れない)。画像が正方形になったので、ロースターカード(132px)・雇用候補カード(96px)・詳細ビュー(96px)の画像枠も、横長に伸ばさず正方形のまま表示するようにした(以前は枠がカード幅に伸びて、正方形だと帽子や耳の先が上下で切れていた)。

**肖像画像の追加(2026-09-20)**: 同じ番号付きシートの続き`char_49`〜`char_64`の16枚を、同じ加工を通して追加した(計64枚)。全16枚を抽選対象とし、旧家の血筋+2(聖職者風の青いフード・本を持つ星の魔女帽)、森人の血+4(弓使い・ドライアド・リュート弾き・花冠の聖女)、王家の落胤+2(冠をのせた悪魔・金の冠飾りの竜人風)、平民+8(海賊・獣人3・トカゲ人・歯車帽の技師・炎の精霊・道化師)に振り分けた。既存ファイル名の中身は変えていないので、旧セーブの見た目は変わらない。

### 4.3 スキル

初期スキルカテゴリ（6分類、2026-09-15に「回復」追加）:

| スキル | 用途 |
|---|---|
| 知恵 | リドル等の謎解きを突破する |
| 鍵開け | 施錠された扉を開く |
| 破壊 | 障害物を破壊して突破する |
| 知覚/発見 | 隠し通路・隠された道に気づく確率を上げる |
| 戦闘力 | ボスや危険な生物との戦闘 |
| 回復 | 毎日、パーティ内の負傷者のHPを自動で回復する(2026-09-15追加。5.4節参照) |

**状態・レベルの表示(2026-09-13実装)**: 探索者管理パネルとロースター一覧に、状態(探索中/回復中(あと何日か)/未割当)と5スキルのレベル一覧を表示する。特に戦闘敗北後の「回復中」はそれまでUIのどこにも出ておらず、プレイヤーから見て「なぜ探索が進まないのか」が分からない状態になっていた。

**ロースター一覧のカード型UI(2026-09-13実装、同日中に正方形ポートレートカードへ作り直し)**: 血筋・担当・状態を1行の文字列に詰め込むと、情報が増えるたびにはみ出して読めなくなる(「文字だけでは表現に限界がある」)ため、探索者ごとに素のControlで組んだカード行に作り直した。当初は横長の行(頭文字アイコン・名前・担当セクション・HPバー・状態バッジを横並び)だったが、将来探索者ごとの正方形画像に差し替える想定を見据えて`[正方形画像]`の下に`[名前][状態バッジ]`を積む縦長のポートレートカードへ再設計し、`GridContainer`で並べるようにした(画像は未実装のため、血筋で色分けした正方形+頭文字で代用。担当セクション名とHPバーはカードからは外し、詳細ビュー側に統合)。

**カード横幅のはみ出し修正(2026-09-13)**: 上記カードの横幅を「ポートレート96px+当て推量24px」で決め打ちしていたため、「アーチボルド」のような長めの名前だと名前+状態バッジの行がカード右端を越えてはみ出す不具合があった(`Button`は`VBoxContainer`等の`Container`と違い、子要素の必要サイズを自分の最小サイズへ反映しないため、当て推量の値が小さすぎても実行時に警告なく素通りしてしまう。詳細は[[godot_install_path]]参照)。カード幅を余裕を持った固定値(190px)に広げると同時に、名前ラベル側にも`clip_text`+`text_overrun_behavior=OVERRUN_TRIM_ELLIPSIS`による省略表示を安全弁として追加し、カード自体に`tooltip_text`でフルネームを確認できるようにした。これにより、想定よりさらに長い名前が来ても再び無警告ではみ出すことはない。

**探索者管理パネルの一覧/詳細2ビュー構成への再設計(2026-09-13)**: 当初はロースター一覧(左)と選択中探索者の操作(担当セクション割り当て+スキル訓練、常時表示、右)を左右に並べた固定2カラムだったが、情報が増えるたびに右側が縦に伸び続け窮屈になっていた。ポートレートカードの一覧のみを表示する「一覧ビュー」を既定表示にし(担当・スキルは一覧には出さない)、カードをクリックすると同じ領域が「詳細ビュー」に切り替わる方式に変更した。詳細ビューは`TabContainer`で[ステータス(HP/状態/担当セクション名の要約＋スキル訓練)][担当(セクション割り当てTree・割り当て/ログ/予測ボタン・完全踏破後の設定)]の2タブに分け、常時2カラムで詰め込んでいた旧UIより縦横それぞれを広く使えるようにした(担当セクションのTreeが余裕のある高さを持てるようになった)。マップの探索者アイコンをクリックした場合は一覧を経由せず直接その探索者の詳細ビューを開く(`_open_npc_panel(show_detail)`)。詳細ビューの「← 一覧へ戻る」ボタンで一覧ビューに戻れる。

成長方法は以下の両輪:
- **経験値型**: 探索で該当スキルを使うことで自然に上昇する。知覚（発見試行のたびに）だけでなく、知恵・鍵開け・破壊（ゲート挑戦のたびに、成否を問わず）・戦闘力（戦闘の実ラウンド数分）も同様に、使うたびに経験値が入る。**資金を使わなくても、時間をかけて挑戦し続ければいつかは育つ**（5.2節の「試行回数がものを言う」思想を全スキルに適用。無課金プレイでも詰まりきらない）
- **資金ブースト**: 利益を使って明示的に訓練し、成長を加速できる。訓練コストは**現在のスキルレベルが高いほど高額になる**（一般的なインクリメンタルゲームの成長カーブ。次の一歩が徐々に重くなる）

### 4.4 雇用フロー

「雇う」＝募集をかける操作。募集をかけると、能力・先天的特性の異なる候補が複数人提示され、プレイヤーが選んで雇用する（ガチャ的な選択感）。

**雇用コスト**は候補の質によって変動する。能力値が高い、あるいはレアな先天的特性を持つ候補ほど雇用コストが高額になる。プレイヤーは「安く平均的な人材」か「高くて優秀な人材」かを都度選べる。

募集の発行タイミングは**プレイヤーが任意のタイミングで自由に行える**（月次などの制限はない）。雇用上限とコストのみが実質的な制約となる。

**コスト構造**: 募集を掛ける行為自体にコストが発生する（候補を見るだけでも課金される）。気軽に何度も募集を乱発できないようにし、雇用の意思決定に重みを持たせる。

**名前の自動割り振り(2026-09-13実装)**: 候補の名前は、8.1節と同じ「実行時にAPI生成しない」方針に合わせ、開発時にオフラインで用意した名前辞書(`name_generator.gd`)から抽選する。血筋（平民/旧家の血筋/森人の血/王家の落胤）ごとに雰囲気の異なる名前リストを持ち、候補生成時に決まった血筋に応じた名前を割り当てる。

### 4.5 雇用上限

同時に雇用できる探索者数には上限がある。上限は施設やプレイヤーのレベルによって拡張可能（成長カーブの一要素）。

施設拡張は、探索で得た利益と**同じ資金プール**を消費して行う（雇用・スキル強化・施設拡張が同じ資金を奪い合う3択のトレードオフになる）。

### 4.6 担当エリア

1人のプレイヤーが雇用する複数探索者は、同じマップを共有するのではなく、**探索者ごとに担当セクションを分担**して探索する。並列探索により重複を避け、マップ全体を効率的にカバーできる。

**マップ上の表示(2026-09-13実装、同日中に表示位置を変更)**: どの探索者がどのセクションを担当しているか一目で分かるよう、探索者ごとの小さなアイコン(現状は名前の頭文字のみ。将来的には探索者個別の画像に差し替える想定)を表示する。クリックすると探索者管理パネルでその探索者を選択した状態で開く。当初はセクション枠の見出し下にまとめて表示していたが、どのフロアで今動いているか分からないという指摘を受けフロア単位の表示に変更した(詳細は5.3節末尾)。

**割り当て候補の絞り込み(2026-09-13実装)**: 担当セクションの選択肢は、既に誰か(雇用/野良問わず)が到達しているか、隣接する突破済みノードから発見を試みられる状態(`WorldMap.is_section_reachable()`)のセクションだけに絞る。世界のどこからも繋がっていない未到達地帯を選んでも実際には何も進行しないため、そもそも選択肢に出さない(該当セクションが1つも無いエリアごと非表示になる)。

探索者を切り替えるたびに、担当セクションの選択肢(Tree)もその探索者が現在割り当てられているセクションを選択済みの状態にする(以前選んでいた探索者の選択状態が残ったままにならないように)。

担当エリアの単位は**セクション（5.1のワールド階層）**とする。探索者は1つのセクションに割り当てられ、そのセクション内のフロアのみを探索する。1セクション＝1ダンジョン、あるいは1つの町周辺エリアのように、ノードグラフ上の意味のあるまとまりが担当割り当ての最小単位になる。

**2026-09-14更新(実装済み)**: 上記の「探索者ごとに担当セクションを持つ」という割り当て単位は、パーティ制度の導入に伴い「パーティごとに担当セクションを持つ」に置き換わった。個々の探索者は単独では担当セクションを持たず、必ずいずれかのパーティに所属した状態で割り当てられる(未所属の探索者も存在できる)。詳細は4.7節。

### 4.7 パーティ制度(2026-09-14実装済み)

**背景**: 当初は探索者1人が単独で担当セクションを探索する設計だったが、以下の理由からパーティ単位に変更する: (1) 敵の強さを奥のエリアに向けて今後もインフレさせていきたいが、探索者単独のままではすぐ頭打ちになる、(2) 装備システム(6.2節)の導入にあたり、複数人で役割分担する方がRPGらしい手応えが出る。

**編成**:
- 1パーティは固定4人。雇用探索者の中から4人選んで編成する(1人の探索者は同時に1つのパーティにしか所属できない)。
- パーティ内には並び順(戦闘での対戦順、5.4節参照)があり、プレイヤーが自由に並び替えられる。
- パーティは複数編成できる。各パーティが従来の探索者と同様に別々のセクションを並列で担当する(担当割り当ての単位が探索者からパーティに変わるだけで、「並列探索でマップ全体をカバーする」という思想自体は4.6節から維持)。

**初期パーティ(無償、2章参照)**:
- ゲーム開始時、プレイヤーには購入・募集不要で4人パーティが1つ用意されている。
- メンバーの得意スキルが偏らないよう配分する(例: 知恵・鍵開け・破壊・戦闘の各担当が1人ずつ、など)。完全ランダム抽選にはしない。
- 血筋は平民中心とし、レアな血筋(旧家の血筋/森人の血/王家の落胤)は通常の雇用でのみ入手できるようにする(初期パーティを無償にしたことで雇用そのものの特別感が薄れないようにするため)。
- 装備は最下級の「木」等級から開始する(6.2節)。
- 2つ目以降のパーティのメンバーは、従来通り募集・雇用(4.4節)で集める。

**ゲート判定(スキル/血筋/所持品)**:
- 知恵・鍵開け・破壊・知覚のスキルゲート、および血筋ゲートは、パーティ内で該当パラメータが最も高い(条件を満たす)メンバーの値で判定する(5.3節のゲート種別自体は変更なし)。
- 所持品ゲートも同様に、パーティ内の誰か1人がそのアイテムを持っていれば通過できる(パーティ内OR判定)。アイテムの所持自体は引き続き個人所持のまま(パーティ共有インベントリは導入しない)。
- スキル経験値は、その判定を担った(＝該当スキルが最も高かった)メンバーに入る。結果としてパーティ内で自然に「知恵担当」「鍵開け担当」のような役割分担が育っていく想定(意図した副次効果)。

**戦闘**: 5.4節を参照。

**収入・攻略報酬(6.1節)への影響**: 月次収入・攻略報酬の対象は「セクションに配置された探索者」から「セクションに配置されたパーティ」に置き換わる。計算式自体(累計突破フロア数×セクション倍率)は変更しない。

### 4.8 ジョブ・固有スキル(2026-09-14実装済み。固有スキルプールの拡充と転職UIは11章参照)

**位置づけ**: ジョブは血筋(4.2節)と同様、雇用時(候補提示時)に決定される**半固定**の属性。ただし血筋と違い、特定のアイテムを消費し、かつ条件を満たすことで後から**転職**できる(可能になるのはゲーム後半〜終盤を想定。将来シナリオ機能(3章の`start_year`/`start_month`と同様、将来の拡張のためのフック)が実装された際には、シナリオによって転職自体を禁止する選択肢も用意できるようにしておく)。

**2026-09-14実装済み**: 消費アイテム「転職の秘薬」(`reclass_elixir`)を新設し、4〜9番目のエリアそれぞれの手強い戦闘ゲート1箇所ずつ(いずれも既存の報酬チェーンに含まれない箇所)に`item_reward`として設置した(同じアイテムIDなので複数箇所から繰り返し入手できる)。探索者管理パネルの詳細ビューに転職先ジョブの選択(OptionButton)と「転職する」ボタンを追加し、該当アイテムを所持している時だけ押せるようにした(`Items.consume()`を新設)。転職すると装備している武器・防具は自動で外れる(新ジョブでは種類が合わなくなるため、`Npcs.change_job()`内で処理)。スキルLv・経験値・固有スキルは維持される。

**ジョブ一覧**: 既存の5スキル(4.3節)に1対1で対応する5職を用意する。パーティは4人編成(4.7節)のため、毎回どれか1職の恩恵を諦める編成選択が生まれる。

| ジョブ | 得意スキル | 装備適性(武器/防具カテゴリ、6.2節参照) |
|---|---|---|
| 戦士 | 戦闘力 | 剣 / 重装備 |
| 重戦士 | 破壊 | 大槌 / 重装備 |
| 盗賊 | 鍵開け | 短剣 / 軽装備 |
| 賢者 | 知恵 | 杖 / 法衣 |
| 斥候 | 知覚 | 弓 / 軽装備 |

**ジョブの効果**:
- **得意スキルの成長ボーナス**: 得意スキルの経験値獲得量が1.5倍になる(4.3節の自然成長・戦闘のラウンド数分の経験値のいずれにも一律で乗算する)。訓練コスト(資金ブースト)自体は変更しない。
- **装備制限**: 各ジョブは対応する武器の種類、および対応する防具カテゴリ(重装備/軽装備/法衣の3カテゴリ、上表参照)のみ装備できる。転職すると、以後装備できる種類も新しいジョブのものに切り替わる(転職前に装備していて新ジョブでは使えなくなる装備をどう扱うかは実装時に検討)。
- 転職してもスキルLv・経験値、固有スキル(下記)自体は変化しない。変わるのは「今後どのスキルが伸びやすいか」と「装備できる種類」のみ。

**固有スキル**:
- 探索者1人ごとに、雇用時にジョブに応じた固有スキル候補プールから1つランダムに抽選して割り当てる(`name_generator.gd`の血筋別名前抽選と同じ仕組み。プレイヤーからは「この探索者だけの個性」に見えるが、実装上はジョブ別の事前定義プールから引く形にすることで、コンテンツ量と調整コストを現実的な範囲に抑える)。
- 一度割り当てられた固有スキルは、その探索者が転職しても変化しない(血筋と同様、後から変わらない個人の資質として扱う)。
- 効果の系統はジョブによって戦闘寄り/探索寄りに分かれる。戦士系(戦士/重戦士)は戦闘中に発動する効果、探索系(盗賊/斥候)はゲート判定に影響する効果、賢者は両方の性質を持つ効果があってもよい、というのが大まかな傾向。

  **2026-09-14実装済み**: ジョブごとに8種(計40種)を`unique_skills.gd`に実装した。効果の系統は
  各ジョブ3〜4パターン×複数段階(例: 戦士は「先頭時戦闘力+30/40/50%」「常時戦闘力+α」
  「最大HP+α」の3系統を段階違いで8種)。上記の例示時点では「成功率+20%」という説明文だったが、
  該当するskillゲートの判定は確率ではなく閾値判定(`スキルLv >= min_level`)のため、実装時に
  「実効スキルLv+2」のような表現に読み替えている(効果の意図は変えていない)。実装にあたり、
  当初の3効果種別(`front_combat_power_pct`/`gate_level_bonus`/`discovery_pct`)に加えて
  `combat_power_flat`(常時戦闘力+固定値)と`max_hp_flat`(最大HP+固定値、雇用時に一度だけ適用)の
  2種を追加した(`npcs.gd`)。

## 5. 探索

### 5.1 マップ構造

**ノードグラフ**（場所＝ノード、道＝エッジの接続関係の集合）。座標を持つ2Dグリッド/タイルマップではない。プレイ画面ではこのノードグラフを視覚的に表示する（ノード図・簡易マップ画面）。

**規模感**: 1ワールドあたり**中規模（数百ノード）**を目安とする。数ヶ月単位のプレイで少しずつ地図が埋まっていく規模感。

**ワールド階層（エリア／セクション／フロア）**: ワールドは3階層で構成する。
- **エリア**（国や地方など最上位区分）
- **セクション**（ダンジョンやフィールドなど、4.6の担当エリア割り当ての単位）
- **フロア**（ノードグラフ上の個々の場所。1つ1つが探索の最小単位）

セクションはマップ画面上でも視覚的に1つの枠として表示される（当初はGodotの`GraphFrame`機能を使っていたが、10章の通り素のControlノードによる自前描画に置き換え済み）。現時点では階層は表示・担当割り当て・掲示板の集約単位（7.1）としての意味を持ち、「セクション入場条件」のようなゲームルール上の追加制約は設けていない（個々のフロアのゲート条件はフロア単位のまま）。

**エリア間移動の支援(2026-09-13実装)**: マップが縦に長くなり、下の方のエリアまでスクロールするのが大変になったため、マップ上部にフロートで全エリア名のボタンを並べ、クリックするとそのエリアの先頭セクションの位置まで自動スクロールする機能を追加した。

**エリアの可視化(2026-09-13実装)**: セクション枠だけではエリア名がマップ上のどこにも表示されず、「小さな王国」がどこからどこまでを指すのか分からない問題があったため、所属セクション群を外接する大きな背景枠とエリア名の見出しを、セクション枠より背後に追加した。フロート表示のエリア選択バーがこの見出しの真上に重ならないよう、余白計算にバーの高さ分の余白(`MAP_NAV_BAR_CLEARANCE`)も加味している。

**フロア詳細のダブルクリック表示(2026-09-13実装)**: マップ上でフロアの箱をダブルクリックすると、そのフロア単体の詳細(所属セクション・状態・ゲート条件を人間可読にした説明・突破報酬アイテム・そのフロアに絞った行動ログ)をポップアップ表示する。フロアの箱に当たらなかった場合はセクション枠として扱い、そのセクションの掲示板スレッドを開く(探索者管理パネルの「このセクションのログを見る」ボタンと同じ処理を共有)。

**マップ全体構成のタブ化(2026-09-14実装済み)**: 旧来のフロート型エリア選択バー(クリックでそのエリアまでスクロール)は、9エリア分のセクションを1列に縦積みし続ける方式のため、下に行くほどマップが際限なく長大化する問題を抱えていた。特に、本筋から分岐する条件付きエリア(忘れられた地下墓地/精霊界/月魄の湖/妖精の隠れ里/結晶の深淵/業火の火口)は、実際に足を踏み入れられるようになるまでずっと画面の奥に居座り続けるだけで、進めない間はただの邪魔になっていた。これを解消するため、エリア選択バーを実際の**タブ**(`ButtonGroup`による排他選択、`_active_area_id`が現在表示中のエリア)に変更し、選んだエリアのセクションだけを表示する方式に切り替えた。マップの自動レイアウト(`_compute_node_positions`)も1エリア分だけを対象にすることで大幅に簡略化され、以前あった「エリアの背景枠+見出し」(`_create_area_panel`)は不要になった(タブ自体がエリア名を示すため)。エリア同士の接続(支線の分岐元など)は、分岐元ノードのそばに「→エリア名」という小さなリンクボタン(`_create_area_link`)を表示し、クリックで該当タブへ切り替える形にした(離れたエリアまで実際に接続線を引くことはしない。`_on_map_canvas_draw`は`node_centers`に無い=表示中エリア外のノードへの接続を自然にスキップするだけで対応できた)。未到達のエリアのタブには🔒アイコンを添える(`WorldMap.is_area_reachable()`を新設、`is_section_reachable`のエリア単位版)。実際にウィンドウを起動してのスクリーンショットで、タブ切替・推奨戦力表示・エリア間リンクの表示を確認済み。

### 5.2 発見（隠し通路）

- 指定スキルがないと進めない場所がある
- 行ける道や隠し通路に気づくかどうかは、探索中に**自動で判定される副次的な確率**（プレイヤーが明示的に「捜索しろ」と指示する必要はない）
- 知覚/発見スキルが高いほど気づく確率が上がる。特定パラメータ（先天的特性）を持つ探索者のみ気づけるケースもある
- 前提条件を満たさないと進めない場所もある
- とにかく試行（日々の探索）を重ねることで開ける。十分な試行数がないまま終わる（何も気づかず終了する）こともある。回数がものを言う設計

**自動探索ループ（日次処理）**: 担当セクションに割り当てられた探索者は、1日ごとに以下を行う。
1. **ゲート再判定**: 「発見済みだが進めない」フロアについて、現在のスキル値/戦闘力でゲートを無音に再判定する（会話は開かない。突破できたらその場で「突破済み」に切り替わり掲示板に記録）
2. **発見試行**: 担当セクション内で、通過済みフロアに隣接する未発見フロア**全てに対して並列に1回ずつ**、知覚スキルに応じた確率で発見を試みる（隣接元は他セクションの通過済みフロアでもよい。例: ダンジョンの入口が村側からつながっている場合）

知覚スキルは発見を試みるたびに経験値を得て自然成長する（4.3節）。

### 5.3 障害・扉

見つけても、条件を満たさないと進めない。突破方法の例:
- リドル → 知恵が高くないと進めない
- 血筋 → 特定の血筋を持つ探索者でないと開かない
- 特定アイテムの所持
- 鍵開け・破壊スキルによる突破

**アイテム所持ゲート**: 特定ノードを突破した際、発見者に固有アイテムが渡ることがある（`item_reward`）。そのアイテムを所持している探索者だけが対応する`item`ゲートを通過できる。アイテムは探索者個人の所持品であり、パーティ共有ではない（例: ボスを倒した探索者自身が、そのすぐ先にある宝物庫を護符で開ける、という一本道の連鎖として機能する。現状は簡易的な「所持フラグ」のみで、アイテムの取引・売却・複数個所持などは未実装）

基本は**1探索者単位で完結**する設計（複数探索者の同時協力が必須になるギミックは現状想定しない。将来的な拡張候補ではある）。

ノードは3状態を取る: **未発見** → **発見済みだが進めない**（ゲート未突破。地図上に見えている）→ **突破済み**（先の探索が可能）。ゲートの通過/失敗は常に探索者のスキル値で自動判定され、7.3の会話ウィンドウは結果を決めるものではなく演出専用（特別にフラグを立てたノードのみ、初回発見時に一度だけ再生される）。これにより、通常のゲート判定では毎回会話が挟まらず、放置系としてのテンポを崩さない。

**マップ表示の色分け（2026-09-13〜）**: found/passed自体は7.1の通り世界共通のグローバル状態のままだが、マップ表示専用に「雇用探索者自身がそこへ到達済みか」（`found_by_employed`）を別途記録し、3色に塗り分ける。
- **自身**（雇用探索者が到達済み）: 明るい色＋ボーダー付き
- **誰か**（野良探索者のみが発見。雇用探索者はまだ未到達）: 通常色
- **未踏破**（誰も到達していない）: 暗い色、かつ名前を伏せて「????」と表示する（発見するまで実際の地名は分からない）

さらに「発見済みだが進めない」ノードは、上記3色のどれであっても半透明にし、突破待ちであることを一目で示す。雇用探索者が後から野良探索者発見済みの場所に到達（発見/突破）すれば、そのノードは自動的に「誰か」から「自身」へ切り替わる。プレイ開始地点（始まりの村/森の入口）は常に「自身」扱いとする。

**「誰か」から「自身」への切り替えバグ修正(2026-09-13)**: ゲートの無いフロアを野良探索者が先に発見・突破してしまうと`found=true`になった時点で、雇用探索者の日次処理(未発見フロアへの発見試行)の対象から永久に外れてしまい、担当の雇用探索者が実際にそのセクションで稼働していても「誰か」色から二度と「自身」色へ切り替わらない不具合があった(「ささやきの森」の入口フロアで発生を確認)。担当探索者が稼働中の日は、既に突破済みだが自分の踏破扱いになっていないフロアを合流させる処理(`Exploration._claim_wild_progress()`)を追加して修正。

**担当探索者アイコンの表示位置(2026-09-13変更)**: 当初はセクション枠の見出し下に、担当探索者の頭文字アイコンをセクション単位でまとめて表示していた。どのフロアで今動いているのか分からないという指摘を受け、フロア単位の表示に変更した(`_current_node_for_npc()`)。担当探索者はセクション内の未発見フロア全てに同時並行でアタックする実装のため厳密な「現在地」は存在しないが、表示上は(1)発見済みだが未突破のゲートがあればそこ、(2)無ければ既知の最前線(未発見フロアに隣接する突破済みノード)、(3)それも無ければ(完全攻略後など)セクション最後のノード、の優先順で代表フロアを決め、そのフロアの箱にアイコンを表示する。

**未到達セクションの明示(2026-09-13追加)**: `WorldMap.is_section_reachable()`がfalseのセクション(まだ誰も足を踏み入れておらず、隣接する突破済みノードも無い)には、セクション枠の下に「🔒 未到達」ラベルを表示する。ダブルクリックすると、他セクションから繋がる入り口ノードのうちまだ通れないものを列挙する詳細ウィンドウを開く(未発見の入り口ノードは名前を伏せる)。

### 5.4 戦闘(2026-09-14パーティ制へ変更、実装済み)

ボスや危険な生物との遭遇はHP・戦闘力パラメータを持つ戦闘として存在する（純粋なスキル判定・パズルではない）。パーティ制度(4.7節)の導入に伴い、以下のように解決方式を拡張する。

- 解決方式: 基本は自動（戦闘力の比較で進行）。プレイヤーの介入は**事前設定型の方針**として行う。戦闘発生の都度リアルタイムで選択を迫られることはなく、放置系としての一貫性を保つ
  - **発動条件**: HP割合のみ（例: 「HPが30%以下になったら発動」）。シンプルな1種類のしきい値に絞る
  - **発動後のアクション**: (1) アイテム使用（回復・逆転アイテムなど）、(2) 撤退判断（深追いせず自主的に退く）の2種類を探索者ごとに事前設定できる（`combat_policy`はメンバー個人ごとに持つ）
- **パーティ内の戦闘順序**: プレイヤーがパーティ編成時に決めた並び順(4.7節)で、メンバーが1人ずつ順番に同じ敵と戦う
- **敵の戦闘力の引き継ぎ**: 先頭のメンバーが自分の方針(撤退)に従って戦線を離脱すると、次の並び順のメンバーが**そのときの敵の残り戦闘力を引き継いで**続けて戦う。「1人目が敵を消耗させてから、決め手のメンバーを投入する」といった戦術が成立する
- **パーティ全体の敗北**: 並び順の全メンバーが撤退または戦闘不能になった場合、パーティ全体がそのセクションから退却し、**全員まとめて**一定期間の回復待ちに入る（個々のメンバーが独立して回復するのではなく、パーティ単位で足並みを揃える）。雇用探索者が永久に失われることはない（安全設計）という方針は維持
- 回復期間が明けるとHPは全回復し、探索を再開する
- **勝ち目のない敵には挑まず、力を付けに退避する(2026-09-20)**: 戦闘に乱数は無く、同じ戦力なら結果は毎回同じなので、勝てない相手に挑んでも全滅して休養に入るだけだった(休養が明けた同じ日に、再び同じ敵に全滅する循環。マップでは休養中のパーティが動かず、HP1のまま同じ敵に挑み続けるように見えた)。そこで、満タンのHPでも勝てない(`Combat.predict_party_result(..., assume_full_hp=true)`が勝利でない)戦闘ゲートには挑まない。担当セクションで、発見済みで未突破のフロアが「勝てない戦闘ゲートだけ」になり、発見できるフロアも残っていない時に、世界の並び順で**1つ前の攻略済みセクション**へ退避する(無ければ世界の最初のセクション。退避先が今のセクション自身ならその場で待機)。退避中はパーティ全員が戦闘力の経験値を毎日`RETREAT_TRAINING_EXP_PER_DAY`(=1)得て、戻り先のフロアに勝てる見込みが立った日に、元のセクションへ戻る(掲示板に記録)。退避中は「先へ進む」で先のセクションへ動かさない。プレイヤーが手動で割り当て直すと退避は解除される。技能ゲートなど他に挑めるフロアが残っている間は退避しない。
- **経験値**: 実際に戦った各メンバーが、自分が戦ったラウンド数分の戦闘力経験値を得る（4.3節の「使うたびに経験値」の考え方をそのまま維持）
- **勝利**: 敵の戦闘力を0以下にできれば、その時点で戦っていたメンバー(および既に交代済みのメンバー全員)がそのまま探索を継続する
- **マップ上の扱い**: 戦闘はゲートの一種（`gate.type == "combat"`）として実装されており、5.3のスキル系ゲートと同じ枠組みで自動探索ループに組み込まれている。「アイテム使用」方針は根気強く戦い続ければ理論上いつか勝てる安全策、「撤退判断」は早めに損切りして再挑戦の機会を待つ方針、という役割の違いがある
- **勝利したが個別に撤退したメンバーがいる場合の回復(2026-09-15修正)**: パーティ全体が敗北した場合だけでなく、**勝利はしたが途中で個別にRETREAT方針で戦線離脱したメンバーがいる場合**も、パーティ全体を3日の療養に入れHPを全回復させる。以前はこの判定が「戦闘不能(hp<=0)になったメンバーがいるか」だけを見ており、個別撤退(HPが1付近まで減るがhp<=0にはならない)だけのケースが漏れていたため、「勝利したのにHPが1のままのメンバーが、療養も無いまま翌日以降も平然と次の戦闘に挑んでしまう」という不具合になっていた
- **「回復」スキルによる日次HP回復(2026-09-15追加)**: 上記の療養(=パーティ全体の停止を伴う)とは別に、探索を止めずに少しずつHPを持ち直せる手段として「回復」スキル(4.3節)を追加した。パーティ内で最も「回復」が高いメンバーが、毎日HP満タンでない仲間を`5 + 3×Lv`だけ回復させる(Lv0でも最低限は回復する。4.3節「無課金プレイでも詰まりきらない」方針を踏襲)。実際に誰かを回復させた日だけ、その担当者に経験値が入る
- **未割当(ホーム)状態は毎日全回復(2026-09-15追加)**: パーティを担当セクションから明示的に外す(未割当=IDLE状態にする)と、「ホームに留まっている」ものとして扱い、毎日その場でHPを全回復させる。探索中の「回復」スキルによる緩やかな回復より速く確実にHPを戻したい場合、プレイヤーが担当を外すという分かりやすい手段を選べる

**戦力(パワー)スコア**: 6.2節参照。マップ上で各セクションの「推奨戦力」と、パーティの現在の戦力を見比べられるようにする。

**撤退時のヘルプメッセージ(2026-09-14実装済み)**: 8.1節で触れた「即死の壁」構造(`enemy_power - combat_power`が一定以上で即敗北する)は、初見のプレイヤーには「なぜ勝てないのか」が伝わりにくい。そこで、戦闘ゲートで撤退・敗北した際に掲示板(該当セクションのスレッド)へ「①武器防具屋で装備を強化する ②探索者管理パネルで「戦闘力」スキルを訓練する ③何度も挑み続ければ戦闘の経験値で自然に強くなる」という3つの対策を案内するメッセージを投稿するようにした(`exploration.gd`の`_post_retreat_help()`)。敗北・撤退したパーティは`Parties.retreat_and_recover()`により数日は再挑戦できないため、この投稿も実質「回復サイクルごとに1回程度」の頻度に自然と収まり、日次でスパムになることはない。

## 6. 経済

### 6.1 収入(ワーカー配置型、2026-09-13実装)

資金の獲得経路は当初「探索で得た利益」とだけ構想されていたが、具体的な収入源が長らく未実装だった。以下の**ワーカー配置型**(スタークラフター系インクリメンタルゲームの資源ノード配置に近い)で実装済み:

**2026-09-14注記(実装済み)**: パーティ制度(4.7節)の導入に伴い、以下の「担当探索者」は「配置されたパーティ」に置き換わった。計算式自体は変更していない。

- **月次収入**: 月末の集計タイムに、担当探索者が**現在いる**セクションごとに「そのセクションの累計突破フロア数 × セクション倍率」を資金として得る。配置転換すると元のセクションからの収入は失われる(常駐が前提)
- **セクション倍率**: セクションが所属するエリアの登場順(1始まり)がそのまま倍率になる。後発エリアほど高倍率になり、8.1節の「後発エリアほど規模と難度を緩やかに引き上げる」方針と自然に噛み合う。セクションごとに新規データを追加する必要はなく、エリアを追加するだけで自動的に反映される(`WorldMap.section_multiplier()`)
- **攻略報酬**: セクション内の全フロアを突破(完全攻略)した瞬間に一時金が入る(基礎額×セクション倍率×フロア数)。同一プレイで**本当に最初に**完全攻略したセクションだけ、追加の固定ボーナスが乗る(早期の足がかりを作るための一度きりの後押し)
- **踏破後の挙動設定**: 完全攻略したセクションの担当探索者は、探索者ごとの設定(`Npcs.PostClearBehavior`)に従い「そのまま留まって収入源として維持する(STAY)」か「次の未踏破セクションへ自動的に配置転換される(MOVE_ON、デフォルト)」かを選べる。次のセクションは同じエリア内の未完了セクションを優先し、無ければ次のエリア以降から探す(`WorldMap.next_section_to_explore()`)
- **配置予測(2026-09-13追加)**: 探索者管理パネルの担当セクション選択で「予測」ボタンを押すと、実際には配置転換せずに今月(30日)の見込みだけを計算して表示する(`Exploration.forecast_section()`)。セクション内の未突破フロアを、現在到達済みの場所から辿れる順に「発見にかかる予想日数」(1/発見確率を経路に沿って積み上げたもの)で並べ、月内に到達しうる範囲で探索者が実際に負ける(撤退/敗北になる)戦闘ゲートが無いかを、実際のHP/経験値には触れない非破壊シミュレーション(`Combat.predict_result()`)で調べる。見つかった場合、その戦闘に月内に行き着く確率分だけ予測報酬を割り引いて表示する(撤退が先に来れば、その分の報酬は無いものとして扱う期待値化)。スキル/所持品/血筋のゲートで現状塞がれている先はこの見積もりに含めない(今月中に抜けられる保証が無いため)

探索で得た利益（アイテム・資金）は、単一の資金プールとして扱い、プレイヤーが毎回配分を選べる:
- **拡大**: 募集コスト＋雇用コストを払って新規探索者を雇用する
- **強化**: 既存探索者のスキル訓練（資金ブースト）
- **拡張**: 施設に投資して雇用上限を引き上げる

3つの用途が同じ資金を奪い合うため、「今すぐ人数を増やすか」「今いる探索者を鍛えるか」「将来のために上限を広げるか」というトレードオフがプレイヤーの意思決定の中心になる。

**バランス方針**: 全体的に**テンポ良く拡大できる低フリクション**を志向する。序盤から次の雇用・強化にすぐ手が届く状態を保ち、「常に資金不足で悩む」重さは避ける。

**現在の実装値（初期チューニング。今後プレイテストで調整）**:

| 項目 | 数式・値 | 例 |
|---|---|---|
| 開始資金 | 300 | - |
| 募集コスト | 固定50 | - |
| 雇用コスト | 50 + 質(0〜1)×400 | 平均的人材50〜150、レア人材400〜450 |
| 訓練コスト | 20 × 1.4^現在レベル | Lv0→1: 20、Lv5→6: 107、Lv9→10: 413 |
| 施設拡張コスト | 300 × 1.6^拡張回数 | 1回目300、2回目480、3回目768 |

初回雇用は「募集50＋雇用50〜」で最低100（開始資金300の1/3）に収まるよう調整し、最初の一手を軽くしている。一方で施設拡張の初回コスト（300）は開始資金と同額とし、**施設拡張は中盤以降の目標**として意図的に重くしてある（序盤は雇用・訓練に資金を回す設計）。

### 6.2 装備・戦力(2026-09-14実装済み)

**背景**: パーティ制度(4.7節)の導入に伴い、敵の強さは今後「装備込みの4人パーティ」を基準にインフレさせていく方針(8.1節)。スキル経験値だけでも時間をかければ育つ(4.3節の「無課金プレイでも詰まりきらない」方針は維持)が、それだけでは終盤の敵のインフレに追いつけないようにし、**装備の購入を実質的に必須の成長軸**として組み込む。ここが4.3節の方針からの意図的な逸脱点であり、装備購入という新しい資金の使い道(従来の「拡大/強化/拡張」の3択に4つ目の選択肢が加わる)を作ることで、資金を稼ぐ→装備を整える→奥へ進める→また稼ぐ、という成長ループの実感を強める狙いがある。

**装備スロット**: 探索者1人ごとに武器・防具の2スロット(個人装備。4.7節の通りパーティ共有プールにはしない)。

**材質による等級**: 武器・防具それぞれに、以下の6段階の材質等級を用意する。等級が上がるほど価格・戦闘力補正の両方が上がる。武器防具屋ではいつでも全等級を購入できる(到達エリアによる品揃え解放は設けない。価格だけでバランスを取る)。

| 等級 | 戦闘力補正(武器/防具 各) | 価格(武器/防具 各) |
|---|---|---|
| 木 | +5 | 80 |
| 青銅 | +15 | 180 |
| 鉄 | +30 | 390 |
| 鋼 | +50 | 850 |
| ミスリル | +80 | 1900 |
| オリハルコン | +130 | 4100 |

（初期チューニング値。既存の訓練コスト/施設拡張コストと同様、指数的に上がる価格カーブを意図しており、実装後のプレイテストで調整する）

**種類(ジョブ適性)の軸(2026-09-14追記)**: 上記の材質等級とは別に、ジョブ(4.8節)に応じた「種類」の軸を追加する。武器は剣/大槌/短剣/杖/弓の5種、防具は重装備/軽装備/法衣の3カテゴリ。価格・戦闘力補正は材質のみで決まり(種類による差はつけない)、種類はジョブの装備適性を分けるためだけの軸として機能する(例: 「青銅の剣」も「青銅の杖」も価格180・補正+15で共通)。

**戦力スコア**: 探索者1人の戦力 = `スキル(戦闘力)Lv × 10 + 10`（既存の`combat_power`計算式）＋ 装備中の武器の戦闘力補正 ＋ 装備中の防具の戦闘力補正。パーティの戦力は、パーティ4人分の戦力を単純合算したもの。

**推奨戦力の表示**: 各セクション(ダンジョン)には、そのセクション内で最も`enemy_power`が高い戦闘ゲートの値を基準に「推奨戦力」を算出し、マップ上(セクション枠、または探索者管理パネルの担当タブ)に表示する。あくまで大まかな目安であり、実際に勝てるかどうかの厳密な判定は引き続き6.1節の「予測」機能(`Exploration.forecast_section()`)が担う。

**バランス目標**: 最初のダンジョン(「小さな王国」、6セクション)を、無償の初期パーティ(4.7節)だけで**ゲーム内およそ3ヶ月**かけて踏破できる程度を目安に、敵戦闘力・装備の価格/補正・資金の稼ぎやすさを調整する(あまりポンポンクリアできてしまうと拡張の実感が薄れるため)。

## 7. 掲示板・イベント

### 7.1 内部掲示板

**常設ログ**。プレイヤーはいつでも過去の発見・成果を見返せる。集計タイムでは、その期間分の要約が表示される。

雇用探索者の発見だけでなく、野良探索者による発見も**世界共通の情報**として掲示板に反映される（雇用探索者は「自分の利益のためだけの存在」ではなく、世界全体の探索状況の一部を担う）。

**スレッド化**: フロア単位の発見は頻繁に起きるため、全体フィードには載せず、**所属セクションごとのスレッド**にのみ記録する（プレイヤーはセクションを選んで詳細ログを閲覧できる）。全体フィードには、以下の**節目のみ**を掲載する:
- セクションへの初到達（世界で最初にそのセクションの何らかのフロアが見つかった瞬間）
- エリアへの初到達
- 7.3のイベント（ボス発見など）

これにより、野良探索者の日常的な発見が全体フィードを埋め尽くし、プレイヤー自身の探索者の成果が埋もれる、という問題を避けている。野良探索者も雇用探索者と同じ実データを探索するため、同じフロアが「誰かに先に見つかられて二重に報告される」ことは起きない（世界全体で1つのfound/passed状態を共有する）。

**UI（2026-09-13〜）**: 掲示板は他の機能（雇用/探索者管理/行動ログ/セーブ）と同じく、サイドバーのボタンから開くウィンドウに統合されている。全文・スレッド切替はそのウィンドウ内で行う。ボタン直下には全体フィードの直近10件だけを常時表示する小さなプレビュー欄があり、ウィンドウを開かなくても最新の動きをざっと確認できる。

### 7.2 イベント

ボスや遺跡の発見など。世界から隠されており、条件が整うと発見され、発見後は誰でも認識できるようになる。

表示タイミングはイベントの**重要度・規模で事前分類**される:
- 重要度が高い（ボス発見など世界規模の重大事）→ 即時表示
- 重要度が低い（小規模な発見）→ 月次集計にまとめて表示

### 7.3 イベント会話ウィンドウ

特定条件を満たしたイベント（ボス戦、障害突破、発見イベントなど）は、専用の会話ウィンドウを開いて演出する。ボス戦や謎解きだけでなく、幅広いイベントで共用する汎用の仕組みとする。

- **UI**: 画面下部に固定表示。左右にキャラクター（名前プレート付きの正方形の画像枠。下の「話者の画像」参照）、中央に発言者名とセリフ、必要に応じて選択肢ボタンを表示するオーソドックスなノベルゲーム形式
- **話者の画像（2026-09-20）**: 行の`side`が`left`/`right`なら、その枠に話者の画像を出して明るくする（`main.gd`の`_set_portrait_slot_image()`）。**戦闘の敵は右、人物（衛兵・門番・妖精・チュートリアルの案内人など）は左**という使い分けで、敵は`enemy_01`〜`enemy_32`、人物は町人の`npc_01`〜`npc_32`から選ぶ。画像は話者の名前から`event_portraits.gd`（`EventPortraits.portrait_id()`）が決める: 名前ごとの固定の対応表（敵35種・人物5名）を引き、表に無い名前は種別（ボス戦/戦闘なら敵、それ以外は町人）ごとのプールから名前のハッシュで1枚選ぶ（同じ名前は常に同じ画像、新しい敵や人物を足しても画像が出ないことは無い）。画像は、その枠が別の話者で埋まるか会話が終わるまで残り、話していない行では暗くなるだけで消えない。**`side`が`none`の会話（「古い祠」「宝物庫の扉」のような物の語りやナレーション）には画像を出さない**（扉や祠の名前の横に町人の顔が並ぶのは不自然なため。2026-09-20に、人物が話す会話だけに絞ると決定）。画像の元は`split_npc`/`split_enemy`で、`tools/prepare_portraits.py --no-number`で256x256の正方形に加工して`godot/assets/portraits/`に置いた。敵は35種に対して画像が32枚なので、絵柄が近い敵（ゴーレム・幽霊・竜など）は離れたエリア同士で画像を使い回している
- **時間の扱い**: 会話が開いている間はゲーム内時間を一時停止し、閉じるまで次の進行は起きない
- **進行方式**: 選択肢付き分岐に対応する。プレイヤーの選択によって結果（例: 謎解き成功/失敗、戦闘継続/撤退など）が変わる
- **データ形式**: 会話は「行」の配列で表現する。各行は話者・セリフに加えて、次の行番号（省略時は+1）、選択肢（ラベルと分岐先）、または会話を終了させる`outcome`（結果コード）を持つ。会話システム自体は結果コードを返すだけで、それをどう扱うか（ゲートを開ける、戦闘結果を反映する等）は呼び出し元の各システムが決める疎結合な設計
- **表示スタイル（2026-09-20）**: 会話の種別で、パネルの縁・背景・発言者名・種別バッジ・「次へ」/選択肢ボタンの色を変える。種別は6つ: ボス戦=赤、戦闘=朱、技能=青（通常の進行）、アイテム=金、血筋=紫、案内（チュートリアル）=灰。フロアのイベントの種別はゲートの種類から自動で決まる（戦闘は、そのセクションで最も敵戦闘力が高ければボス戦、そうでなければ戦闘。技能/アイテム/生まれ・血筋のゲートはそれぞれ技能/アイテム/血筋）ので、83本ある会話データには書かない。特別な会話だけ、行に`kind`キーを書いて上書きできる。結果（突破/失敗）は色を変えず、バッジの文字（例:「ボス戦 ― 失敗」）と、失敗時の彩度の低下で示す

## 8. ワールド生成・永続化

### 8.1 生成

マップ・アイテム・障害の内容は、**開発時にClaude Codeを使ってオフライン生成**し、DBに格納する。ゲーム実行中にAPIを呼び出してリアルタイム生成することはしない（APIコスト・レイテンシの問題を回避）。

この規模のデータを扱うため、SQL（DB）での管理が必要。

**現状の実装**: コンテンツ定義はUI（`main.gd`）から分離し、`world_data.gd`という専用のオートロードに集約している（起動時にWorldMapへ流し込むだけの役割）。**コンテンツの正本は引き続き`world_data.gd`のGDScriptコード**（`add_area`/`add_section`/`add_node`/`set_event_scripts`の読みやすい呼び出しのまま、今後もこの形で書き足していく）で、`world_schema_db.gd`が起動のたびにその内容をSQLiteファイル（`user://worldseeker_world_schema.sqlite`、8.2節参照）へスナップショット出力する。DBは「実行時に生成される派生キャッシュ」という位置づけで、DBの行を直接手で編集する運用は想定していない。ノードグラフの画面表示位置は手動指定をやめ、セクションごとのグリッド自動レイアウトに変更済み（ノード数が数百規模に増えてもセクション同士が重ならない）。

現在のワールド内容は**9エリア・39セクション・194フロア**規模まで拡張済み。王国「小さな王国」＝村周辺/古い洞窟/ささやきの森/国境の道/王都/貴族街の6セクション、隣国「レインヴェール」＝郊外/沈んだ遺跡/隠れ森の郷/遺跡の深層の4セクション、隣々国「灰色の山嶺」（レインヴェール郊外の古い物見塔から接続）＝峠道/ドワーフの砦/廃坑/竜の尖塔の4セクション、「忘れられた地下墓地」（王国・貴族街の大聖堂の鐘楼から接続）＝納骨堂入口/白骨の回廊/沈黙の礼拝堂/リッチの聖域の4セクション、「精霊界」（レインヴェール・隠れ森の郷の精霊の祠から接続）＝狭間の境界/漂う島々/鏡影の窪地/星幽の聖域の4セクション、「月魄の湖」（レインヴェール・隠れ森の郷の月の泉の守護者から接続。精霊界とは別の行き止まりから分岐）＝湖畔/沈んだ里/葦の迷路/月宮の4セクション、「妖精の隠れ里」（王国・ささやきの森の古井戸から接続。ゲート無しの行き止まりが起点）＝隠れ里の入口/茸の群生地/悪戯妖精の迷路/妖精の宮廷の4セクション、「結晶の深淵」（灰色の山嶺・廃坑の結晶洞から接続）＝結晶への降下路/晶洞の窪み/共鳴の回廊/結晶の玉座の4セクション、「業火の火口」（灰色の山嶺・竜の尖塔の灰塵の間から接続。9エリア目にして初めて5セクション構成に拡大）＝火口の縁/黒曜石の平原/燠火の坑道/溶鉱の鍛冶場/業火の中心の5セクション。ゲートは知恵（最大Lv5）・鍵開け（最大Lv4）・破壊（最大Lv3）・知覚（最大Lv4）・戦闘（最大敵戦闘力120、業火の王で更新）・血筋（先天的特性、4種のうち3種を使用済み: 王家の落胤/旧家の血筋/森人の血）の全種類を、複数の難易度段階で使用している。アイテムゲートは20系統（ゴブリンの護符/古い探検隊の地図/盗賊の印章/深淵の王冠/ドワーフの鍛冶槌/坑道主の鍵/灰塵の竜鱗/銀の聖遺物匣/砕けたフィラクテリーの欠片/星の欠片/星幽の核/月の真珠/月魄の冠/妖精の粉塵/女王の寵愛の証/共鳴する欠片/結晶の心臓/黒曜石の欠片/業火で鍛えた鋼塊/業火の心臓の計20アイテム）あり、うち1つ（盗賊の印章）は王都で入手し貴族街で使う**セクションをまたいだ**報酬チェーン、残り19個は同一セクション内で完結するチェーン。イベント会話は83箇所に設置。全ゲート種別・複数セクションをまたいだ探索（同一探索者の担当セクション再割り当てを含む）・アイテム報酬チェーンまでシミュレーションで動作確認済み。「数百ノード」目標に対してはまだ規模が小さく、追加のコンテンツ肉付けは今後も継続課題。

**方針（2026-09-12決定）**: 後発エリアほど規模と難度を緩やかに引き上げていく。目安としてセクション数4→5、ノード数19前後→28前後、戦闘ゲートの敵戦闘力上限110→120程度（9エリア目の「業火の火口」で実際に5セクション・28ノード・敵戦闘力120まで適用済み）。過去エリアの遡及的な作り直しは行わず、以降の新規エリアから適用する。敵の強さ自体は依然として`world_data.gd`上でノードごとに手書きする値であり（8.1節の方針通りコンテンツは正本コード直書き）、エリア内では入口から遠いノードほど`enemy_power`を高く設定する、という執筆時の慣習であって、深さから自動算出するランタイム機構ではない。

**敵戦闘力(`enemy_power`)のパーティ換算（2026-09-14決定・実装済み）**: パーティ制度(4.7節)・装備システム(6.2節)の導入に伴い、`enemy_power`を手書きする際の「相場感」を、従来の「探索者1人分の戦闘力」から「装備込み4人パーティの戦闘力」を基準に見直した。数式による自動算出への置き換えは行わない（本節冒頭の「コンテンツはコード直書きが正本」という方針、およびボス戦などでの演出的な強弱づけのしやすさを優先した判断）。

既存36箇所の戦闘ゲート(9エリア・194フロア中)を再チューニングする際、`combat.gd`の実際の計算式を検証した結果、**戦闘は「即死の壁」型で難度が決まる**ことが判明した: `hp -= max(1, enemy_power - combat_power)`という式のため、`enemy_power - combat_power`が「最大HP(100) + 回復方針(USE_ITEM)の1回分の回復量(+30)」＝130以上になると、そのメンバーは初撃で戦闘不能になる(即死の壁)。逆に130未満なら、敵の戦闘力は消耗戦で毎ラウンド最低1は必ず減っていく(`enemy_power -= max(1, combat_power - enemy_power/2)`)ため、USE_ITEM方針であれば時間はかかっても理論上ほぼ確実にいつか勝てる(5.4節「根気強く戦い続ければ理論上いつか勝てる安全策」という記述通りの挙動)。つまり**旧来の値(20〜120)は、装備込みパーティの誰か1人の戦闘力(Lv0でも装備込みで20はある)に対して単なる時間差でしかなく、実質的に「壁」として機能していなかった**(シミュレーションで確認: 旧数値のまま木装備Lv0の初期パーティを走らせたところ、最初の6セクションの大半をものの数週間で素通りした)。

このため、以下の式で全36箇所を再設計した:
- エリアNの「その中で最も手強い戦闘ゲート(概ねボス)」の目標戦闘力を`C_N`、そのゲートの`enemy_power`を`C_N + 100`(即死ラインに30の安全マージン)とする
- `C_N`はエリアが進むごとに+60ずつ増える(材質1段階分の装備更新(武器+防具で+20)や、スキルLv数段分の伸びに相当する現実的な増分)。`C_1=80`(初期パーティ基準の20から+60)を起点に、`C_9=560`(最終エリア)まで積み上げる
- エリア内の下位(非ボス)戦闘ゲートは、ボスの`enemy_power`から20刻みで低い値を割り当て、装備・スキルを段階的に整えながら格下の敵から順にこなしていく手応えを作る

シミュレーションで再検証済み: 装備なし(木装備のまま)だと最初のダンジョン(小さな王国)の2セクション目「古い洞窟」のボス(`boss_lair`、`enemy_power`180)で120日間足止めされ続け、確かに「壁」として機能することを確認。前衛1人に青銅装備(武器・防具、戦力20→40)を購入させても、このボス(必要戦闘力目安51以上)にはまだ届かない(青銅装備だけでは力不足になるよう意図的に設計。先に格下の敵(必要戦闘力31程度)を装備半端な状態でも突破し、そこで得た戦闘経験値も合わせて本命のボスに挑む、という段階的な組み立てを想定)。**この36箇所の具体的な数値は初期チューニング値であり、実プレイでの調整が必要**(11章参照)。

### 8.2 保存・リプレイ

「一度使ったワールドの設定を保存し、リプレイ用に使う」とは、以下の両方を指す:
1. **記録再生**: 特定プレイ回の行動ログを保存し、後から観戦・再生できる
2. **スキーマ再プレイ**: 生成済みのワールド構造（ノードグラフ・ギミック配置など）はテンプレートとして保存し、新しい探索者や別プレイヤーが同じマップにゼロから再挑戦できる

**現状の実装（進行状態の保存/復元）**: `save_system.gd`が`addons/godot-sqlite`(GDExtension、Windows x86_64バイナリのみをリポジトリに同梱)経由でSQLiteファイル(`user://worldseeker_save.sqlite`)に進行状態を保存/復元する。保存対象は資金・雇用探索者名簿(血筋/スキル経験値/所持品込み)・ワールドの発見/突破状態・掲示板ログ(全体+スレッド)。テーブルは`meta`(スカラー値のキーバリュー)・`npcs`/`npc_traits`/`npc_skills`/`npc_inventory`(探索者関連を正規化、JSON blobは使わない)・`world_progress`・`board_entries`/`board_threads`/`board_thread_entries`・`action_log`(後述)の10個。`meta`以下`board_thread_entries`までは保存のたびに全テーブルをDELETEしてから現在の状態を丸ごと再INSERTする(差分更新はしない)。日次(`TimeSystem.day_advanced`)およびウィンドウを閉じたタイミングで自動保存する。あわせて「セーブスロット」パネルに「今すぐセーブする」(手動セーブ、2026-09-13追加)ボタンもあり、オートセーブを待たずに任意のタイミングで明示的に保存できる(分岐前のチェックポイントを作りたい、という要望への対応)。同パネルの「オートセーブを有効にする」チェックボックス(2026-09-13追加、`SaveSystem.autosave_enabled`、`worldseeker_meta.cfg`に永続化)でオートセーブ自体をオフにもできる。オフの間も手動セーブ・進行の複製・新規プレイ開始・スロット切替/削除など、プレイヤーが明示的に行う保存(`SaveSystem.save_game()`を直接呼ぶ経路)は影響を受けない(`SaveSystem.autosave()`という専用の入り口だけがこのフラグを見る)。多探索者・複数セクションをまたいだ状態(血筋/所持品/スキル値を含む)での保存→ロード一致をシミュレーションで確認済み。

**起動時は常に新規プレイ(2026-09-14変更)**: 以前は起動時に前回のアクティブスロットを自動ロードしていたが、コード変更後の動作確認(`--headless --quit`)や診断作業のたびに実セーブへ意図せず触れてしまう事故の温床になっていた(実際に一度、診断コードの戻し忘れにより実セーブの探索者を誤って削除する事故が起きている)。そのため自動ロードを廃止し、`SaveSystem.current_slot_id`は起動直後は常に`NO_ACTIVE_SLOT`(-1、どのスロットファイルにも紐付いていない状態)から始まる。`main.gd`の`_ready()`は`SaveSystem.load_game()`の代わりに`SaveSystem.start_fresh_session()`を呼び、Economy/TimeSystem/Npcs/Parties等を初期化して初期パーティ付きの「まっさらな新規プレイ」をその場でメモリ上に用意する(ディスクには一切触れない)。既存の進行を続けたい場合は、セーブパネルから明示的に「このスロットをロードする」を選ぶ、という一般的なゲームの体験に合わせた。`NO_ACTIVE_SLOT`のまま保存(手動セーブ/オートセーブ/終了時保存のいずれか)が呼ばれた場合は、`save_game()`がその場で空いているスロットIDを新規に割り当ててから保存する(既存スロットを誤って上書きすることは構造上起こらない)。

**現状の実装（記録再生＝行動ログ）**: `action_log.gd`が担当。採用方式は**ログビューアー方式**（決定論的リプレイ＝乱数のシード管理をして同じ結果を再現する方式ではない）。粒度は掲示板と同じ「意味のある出来事のみ」（発見・ゲート突破・マイルストーン。日々のゲート再挑戦の失敗などルーチン判定は記録しない）で、`exploration.gd`の掲示板投稿と同じ箇所から構造化された行を追加で記録する。掲示板の`text`が表示用の整形済み文字列だけを持つのに対し、`action_log`テーブルは`day`/`event_type`/`npc_id`/`node_id`/`section_id`という構造化列を持ち、後から特定探索者やノードで絞り込める。他テーブルと異なり**削除されない追記専用ログ**で、`ActionLog`がメモリ上にバッファした新規分だけを保存のたびにINSERTする。プレイ回をまたいでも区別できるよう`run_id`を発行し、`meta`テーブル経由でセーブ/ロードされる。閲覧用ビューアーUIは`main.gd`の専用パネル（「行動ログを見る」ボタン）として実装済みで、探索者で絞り込める（`SaveSystem.query_action_log()`がその場でDBに問い合わせる。常時メモリに保持はしない）。

**現状の実装（分岐用のスロット複製、2026-09-13追加）**: 「新規プレイを開始する」(`SaveSystem.create_new_slot()`)は進行をゼロから作り直すため、今の進行を保ったまま別の道を試したい(分岐前のチェックポイントを残したい)場合の手段が無かった。`SaveSystem.duplicate_current_slot()`を追加し、セーブスロットパネルの「現在の進行を複製する」ボタンから、今のスロットのファイルをそのまま新しい空きスロットIDへコピーするだけの複製を行えるようにした(WorldMap/Npcs等の再構築は不要で、複製前に`save_game()`で最新状態をディスクへ反映してからファイルコピーする)。複製後もアクティブスロットは元のままなので、複製先は後から「このスロットを開く」で好きなタイミングで辿れる、もう1本のセーブとして残る。

**現状の実装（スキーマ再プレイ＝複数セーブスロット＋ワールドスキーマの複数バージョン管理）**: 8.1節の`world_schema_db.gd`によるワールドスキーマのDB出力（`_write_snapshot()`）に加え、そこからWorldMap/Itemsを再構築する`import_into_worldmap(version_id)`を実装した。`world_data.gd`の`add_area`/`add_section`/`add_node`/`set_event_scripts`呼び出し経路と全く同じWorldMapの公開メソッドを通るため、GDScript直書き経路とDB経由の経路は常に同じ形のWorldMapに収束する。どのノードが「最初から突破済み」（village/forest_edgeなどのスタート地点）かはスキーマDBの`nodes.initially_passed`列に記録し、`world_schema_db.gd`の`_ready()`が`WorldData._ready()`の直後・`SaveSystem.load_game()`より前に実行される（project.godotのautoload順）ことを利用して、実プレイの進行状態と混ざらない「まっさらな初期状態」だけを捉えている。

**複数バージョン管理**: WorldMap/Itemsの内容を正規化したJSONのSHA-256を`schema_version`とし、`user://schemas/schema_<version_id>.sqlite`にバージョンごとの別ファイルとして保存する（内容アドレス方式。同じ内容なら同じハッシュ=同じファイルなので、実際に内容が変わった時だけ新しいファイルが増える）。各セーブスロットは保存のたびに自分が実際に読み込んでいる`WorldSchemaDb.active_version_id`を`meta.schema_version`へ記録する。**2026-09-14変更**: 起動時は常に新規プレイ（上記）になったため、起動時点でのスロットのバージョン差分チェックは廃止した。かわりに`SaveSystem.switch_to_slot()`でスロットを切り替える際に、そのスロット自身の`schema_version`（記録がなければ現行バージョンにフォールバック）で`import_into_worldmap()`し直す。**重要な注意点**: `WorldMap.add_area`/`add_section`/`add_node`と`Items.define`はどれも上書きのみで削除はしないため、`import_into_worldmap()`は必ず先に`WorldMap.reset()`/`Items.reset()`で完全にクリアしてから読み込む（これを怠ると、以前読み込んでいた別バージョンにしかない要素が残ってしまう不具合になる。実際にマルチバージョン切替のシミュレーションでこの不具合を検出し、`reset()`を追加して修正した）。

セーブデータは`user://saves/slot_<id>.sqlite`としてスロットごとに分離し（テーブル定義は共通、パスだけが違う）、アクティブなスロットIDは`user://worldseeker_meta.cfg`で管理する（ただし起動時には読み戻さない。上記の「起動時は常に新規プレイ」参照）。`SaveSystem.create_new_slot(display_name)`は新しいスロットを作り、Economy/TimeSystem/Npcs/Recruitment/Board/ActionLogをそれぞれの`reset()`で初期化し、常に最新の`WorldSchemaDb.current_version_id`でワールドを再構築してから保存する（`display_name`を渡すとそのスロットの名前になる。省略可）。`SaveSystem.delete_slot()`でスロットを削除できる（アクティブな＝現在開いているスロットは切り替え先が定まらないため削除不可、ガードしている）。`SaveSystem.rename_slot(slot_id, name)`で既存スロットの名前を後から変更でき（アクティブでないスロットも、そのスロットのDBを直接開いて`meta.slot_name`だけ書き換えることで対応)、一覧表示は名前が設定されていれば「スロットN」の代わりにそれを使う（2026-09-14追加、スロットを識別しやすくする要望への対応）。UIは`main.gd`の「セーブスロット...」パネル（スロット一覧・切替・削除・名前変更・確認ダイアログ付きの新規プレイ開始ボタン。削除も確認ダイアログ経由）。バージョン管理自体にはUIを設けず、裏側で自動的に動作する。プロセス再起動を模した2バージョン間のシミュレーション（旧バージョンのスロットを継続 → 新バージョンで新規スロット作成 → 両スロットを行き来）で、それぞれが自分の生成時点のマップ形状（ノードの有無・`initially_passed`状態）を正しく保つことを確認済み。

## 10. 技術スタック

- **エンジン**: Godot 4.7（GDScript）。既存プロジェクト（MyCells）と同じ構成で、学習コストを抑える
- **配布形態**: Windowsネイティブ export（.exe）に加え、Android(arm64)のAPKをGitHub Releasesで配布する（2026-09-19〜、ビルドはGitHub Actions、手順は`docs/HANDOFF.md`の「Androidビルド」参照）。まずはローカルで自分だけが遊ぶ想定（9章のマルチプレイ展望とは別に、配布はローカル前提から始める）
- **マップ描画**: 当初はGodot標準の`GraphEdit`/`GraphNode`/`GraphFrame`を流用していたが、ノード・フレームをドラッグで動かせてしまいプレイ中に意図せずレイアウトが崩れる問題があったため、素の`Control`(`Panel`/`PanelContainer`/`Label`、`mouse_filter = IGNORE`でそもそもドラッグ処理を持たせない)による自前描画に置き換えた。ノード間の接続線は`draw_line()`で自前描画。`GraphEdit`はノードグラフ**編集**用のウィジェットであり、読み取り専用のマップ表示には使うべきでないという判断。ScrollContainerだけでは数百ノード規模を動き回りづらいため、キャンバスの空き領域を左ドラッグしてパンできる機能を独自実装で追加した（GraphEditのパン操作の代替）。マウスホイールでのズームも追加済み（2026-09-13〜）: `Control.scale`はScrollContainerがスクロール範囲を正しく再計算してくれないため使わず、ズーム倍率に応じてセル/ノードサイズなどのレイアウト定数を計算し直してマップ全体を再構築する方式にした。カーソル直下のコンテンツ座標がズーム後も同じ画面位置に留まるよう、スクロール位置も再計算する
- **UIテーマ(2026-09-13実装)**: Godotの既定テーマのままだと、押せる/選択できる要素(Button/Tree/ItemList)と、ただの文字(Label)との見た目の力差が乏しく、選択・押下してもわずかにしか色が変わらないという指摘があった。個々のControlごとにスタイルを都度指定するのではなく、`main.gd`の`_build_theme()`でButton/OptionButton/Tree/ItemListの通常/ホバー/押下・選択中/無効の各状態にはっきり彩度差のあるStyleBoxFlatを設定した`Theme`を1つ作り、ルートのControlに設定して以降add_childする全パネル・全ボタンに伝播させている(個々のボタン生成箇所を1つずつ直す必要がない)。押下中/選択中は彩度の高い青にはっきり変える方針
- **永続化**: `GDSQLite`アドオン（`godot/addons/godot-sqlite`、Windows x86_64とAndroid arm64向けバイナリのみ同梱）を2つの用途に使い分けている。(1) `save_system.gd`: セーブデータ（進行状態: 資金・探索者・ワールド探索進捗・掲示板ログ・行動ログ）を`user://saves/slot_<id>.sqlite`に複数セーブスロットとして保存（8.2節）。(2) `world_schema_db.gd`: `world_data.gd`が構築したワールドスキーマを、内容のSHA-256をバージョンIDとして`user://schemas/schema_<version_id>.sqlite`へバージョンごとに保存し、各セーブスロットは自分が生成された時点のバージョンを`meta.schema_version`に記録して、継続/切替のたびにそのバージョンでWorldMapを再構築する（8.1/8.2節）。用途が異なるため意図的に別ファイルに分けている
- **プロジェクト構成**: `godot/` 以下にGodotプロジェクトを配置。主要システムはautoloadシングルトンとして分割（`time_system.gd` / `world_map.gd` / `items.gd` / `world_data.gd` / `world_schema_db.gd` / `npcs.gd` / `wild_npcs.gd` / `recruitment.gd` / `economy.gd` / `board.gd` / `action_log.gd` / `combat.gd` / `event_dialogue.gd` / `exploration.gd` / `save_system.gd`）。スキル種別は `skill_types.gd`（`class_name SkillTypes`）で共有定義。探索者の名前辞書は`name_generator.gd`（`class_name NameGenerator`、血筋ごとの事前生成リスト）で共有定義。`world_data.gd`はコンテンツ定義専用で、UIコード（`main.gd`）から独立している。`items.gd`はアイテム定義と探索者所持品を管理する最小限のシステム
- **自動探索ループ検証済み**: 探索者の雇用→担当セクション割り当て→日次の発見/ゲート突破（スキル・戦闘）→イベント会話の自動発火→掲示板記録までの一連の流れを、シミュレーションで動作確認済み
- **初期スキャフォールド検証済み**: `scenes/main.tscn` + `scripts/main.gd` で、募集→候補提示→雇用、ノードグラフのマップ表示、掲示板ログ表示までの最小ループが実際に動作することをGodotエディタでの起動確認済み
