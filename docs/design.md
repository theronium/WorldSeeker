# ローグライク自動探索 設計ドキュメント

## 1. コンセプト

**世界観**: 中世ファンタジー。魔法・遺跡・血筋・リドルといった要素が自然に馴染む舞台とする。

**ゴール設計**: 明確な終了条件は設けない**エンドレス型**。スタークラフター系インクリメンタルゲームのように、雇用の拡大とNPCの育成を継続的に楽しむことを主眼とする（「クリア」を目的としない）。

OpenWorld的なマップを、技能を割り振ったNPCに探索させる放置系ゲーム。
プレイヤー自身が直接操作するキャラクターはいない（方針指定のみ）。プレイヤーは複数のNPCを雇用し、探索方針（鍛えるスキル・担当エリアなど）を指定するだけで、実際の移動・判定はすべて自動で進行する。

新しく見つかった道や発見は、常設の内部掲示板に記録される。イベントの規模によっては即時に表示され、それ以外は月次の集計タイムでまとめて報告される。

## 2. コアループ

**初期状態**: ゲーム開始時、プレイヤーは雇用NPCを1人も持たない（0人スタート）。最初の募集・雇用がそのままチュートリアル的な導入体験になる。

1. NPCを雇用する（募集をかけ、提示された候補から選ぶ）
2. 雇用したNPCに探索方針・担当エリアを指定する
3. 時間が進行し、NPCが自動で探索・判定を行う
4. 発見や成果が掲示板に記録される（一部は即時、大半は月次）
5. 月末に集計タイムで結果が表示され、時間が一時停止する
6. プレイヤーが内容を確認し、方針を調整してから次の月へ進める（プレイヤーの確認操作が必要）
7. 得た利益（アイテム・資金）を「新規雇用（拡大）」と「既存NPCのスキル強化」に配分する

このサイクルを繰り返しながら、マップの探索範囲・NPCの練度・雇用規模を広げていく。

## 3. 時間システム

- **基準ペース**: 1ヶ月（30日）＝ 実時間25分（等速=1x）。ポモドーロ・テクニックの1セッション分に相当し、「NPCに方針を指定してタイマーを走らせ、他の作業をしながら待つ」という遊び方を想定する
- **倍速機能**: 1x/10x/100x/1000xの段階式（2026-09-13〜、指数的に伸びる方が体感の伸びが分かりやすいとして1x/2x/4x/8x/16xから変更）。UIは1ボタンの順送りクリックではなく、全段階を横に並べたボタン列から直接選ぶ方式（2026-09-13〜）。制限は設けない（戦闘中でも自由に変更できる）。最大1000xで1ヶ月あたり約1.5秒まで短縮できる
- 月末までの残り時間は、控えめな表示（小さなラベルでmm:ss表示）で画面に常設する。ポモドーロ的な巨大なカウントダウン演出はしない
- **暦表示**: カウントダウンとは別に「0年1月1日」のような年月日も常設表示する。暦の起点（開始年月）はデフォルト0年1月だが、`TimeSystem.start_year`/`start_month`として保持しており、将来シナリオ選択機能ができた際にプレイ開始時の年月を差し替えられるようにしてある（現時点ではシナリオ機能自体は未実装で、常にデフォルト値が使われる）
- **セッション型**: ゲームを起動している間だけ時間が進行する。終了している間は進行しない（サーバー側での常時稼働はしない）
- 月末になると自動的に時間が停止し、月次サマリを表示する
- **時間進行の計算方式(2026-09-13、フレームdelta蓄積方式から書き直し)**: 当初は`_process(delta)`のフレームdelta(Godotの計測値)を毎フレーム`_accumulated`に足し込み、閾値(1日分の秒数)を超えた分だけ`while`ループで一気に`_advance_day()`する方式だった。これは「フレームのdeltaが実際の経過時間を正しく反映している」という前提に依存しており、重い`_ready()`直後や`--headless --quit`のような短命プロセスでその前提が崩れると、1フレームで何日分もの`_advance_day()`が連続実行され、日付が瞬時に飛んでしまう不具合があった(初回フレームのdeltaだけを捨てる対策を一度入れたが、それでも起動チェックを繰り返すだけで日付がドリフトする事象が残り、不十分と判明)。**根本的に、Godotのフレームdeltaを信用せず、`Time.get_ticks_msec()`による実時間タイムスタンプの差分から経過時間を計算する方式に書き直した。** さらに、1回のチェックで進められる日数を最大1日に制限し(`if _accumulated >= SECONDS_PER_DAY`、以前は`while`)、それを超える分(遅延)は`_accumulated`に残したまま次回以降のチェックで段階的に追い上げる方式にした(「日付を瞬時に大きく飛ばして帳尻を合わせるより、多少遅延しても後から徐々に追いつく方が良い」という方針)。起動時の基準リセット(`TimeSystem.mark_boot_complete()`)を`main.gd`の`_ready()`の一番最後(UI構築・セーブロードなど重い処理が全て終わった直後)に明示的に呼ぶことで、起動処理にかかった実時間そのものを経過時間の計算から除外している。`--headless --quit`を5回連続で実行しても日付が一切進まないこと、および人為的に60秒分のギャップを与えても1チェックにつき1日しか進まず残りが正しく繰り越されることをテスト用の直接呼び出しで確認済み
- 次の月への移行は自動再開ではなく、プレイヤーの確認操作によって行う（ターン制に近い区切り）

## 4. NPC

### 4.1 種別

- **雇用NPC**: プレイヤーと雇用関係にあり、方針指定に従って探索する。利益・成果はプレイヤーに還元される
- **野良NPC**: 誰にも雇われず、世界の中で勝手に探索しているAI NPC。プレイヤーの利益には直結しないが、発見自体は世界共通の情報として掲示板に反映される（後述）。雇用NPCと**同じワールドの実データ（found/passed）を実際に探索する**存在（フレーバー演出ではない）
  - **できること/できないこと**: ゲートのないフロアは雇用NPCと同様に発見・通過できるが、スキル判定や戦闘が必要なゲートは突破できない（「発見済みだが進めない」状態で見つけるだけに留まる）。実際のゲート突破は雇用NPCの役目
  - **母数**: セクションごとに一定確率で発見が発生する形でシミュレートし、「世界が常に動いている」感覚を演出する
  - **雇用NPCとの関係**: 野良NPCが将来雇用候補として現れることはない。**完全に別の存在・別ロジック**として扱い、雇用候補生成システムとは切り離す

### 4.2 先天的特性（血筋・種族など）

血筋・種族のような属性は、後天的に鍛えられる「スキル」とは別枠で扱う**生まれつきの固定パラメータ**。雇用時（候補提示時）に決定され、訓練では変更できない。特定の血筋でしか開かない場所を作ることで、雇用選択にコレクション性・戦略性を持たせる。

### 4.3 スキル

初期スキルカテゴリ（5分類）:

| スキル | 用途 |
|---|---|
| 知恵 | リドル等の謎解きを突破する |
| 鍵開け | 施錠された扉を開く |
| 破壊 | 障害物を破壊して突破する |
| 知覚/発見 | 隠し通路・隠された道に気づく確率を上げる |
| 戦闘力 | ボスや危険な生物との戦闘 |

**状態・レベルの表示(2026-09-13実装)**: NPC管理パネルとロースター一覧に、状態(探索中/回復中(あと何日か)/未割当)と5スキルのレベル一覧を表示する。特に戦闘敗北後の「回復中」はそれまでUIのどこにも出ておらず、プレイヤーから見て「なぜ探索が進まないのか」が分からない状態になっていた。

**ロースター一覧のカード型UI(2026-09-13実装、同日中に正方形ポートレートカードへ作り直し)**: 血筋・担当・状態を1行の文字列に詰め込むと、情報が増えるたびにはみ出して読めなくなる(「文字だけでは表現に限界がある」)ため、NPCごとに素のControlで組んだカード行に作り直した。当初は横長の行(頭文字アイコン・名前・担当セクション・HPバー・状態バッジを横並び)だったが、将来NPCごとの正方形画像に差し替える想定を見据えて`[正方形画像]`の下に`[名前][状態バッジ]`を積む縦長のポートレートカードへ再設計し、`GridContainer`で並べるようにした(画像は未実装のため、血筋で色分けした正方形+頭文字で代用。担当セクション名とHPバーはカードからは外し、詳細ビュー側に統合)。

**カード横幅のはみ出し修正(2026-09-13)**: 上記カードの横幅を「ポートレート96px+当て推量24px」で決め打ちしていたため、「アーチボルド」のような長めの名前だと名前+状態バッジの行がカード右端を越えてはみ出す不具合があった(`Button`は`VBoxContainer`等の`Container`と違い、子要素の必要サイズを自分の最小サイズへ反映しないため、当て推量の値が小さすぎても実行時に警告なく素通りしてしまう。詳細は[[godot_install_path]]参照)。カード幅を余裕を持った固定値(190px)に広げると同時に、名前ラベル側にも`clip_text`+`text_overrun_behavior=OVERRUN_TRIM_ELLIPSIS`による省略表示を安全弁として追加し、カード自体に`tooltip_text`でフルネームを確認できるようにした。これにより、想定よりさらに長い名前が来ても再び無警告ではみ出すことはない。

**NPC管理パネルの一覧/詳細2ビュー構成への再設計(2026-09-13)**: 当初はロースター一覧(左)と選択中NPCの操作(担当セクション割り当て+スキル訓練、常時表示、右)を左右に並べた固定2カラムだったが、情報が増えるたびに右側が縦に伸び続け窮屈になっていた。ポートレートカードの一覧のみを表示する「一覧ビュー」を既定表示にし(担当・スキルは一覧には出さない)、カードをクリックすると同じ領域が「詳細ビュー」に切り替わる方式に変更した。詳細ビューは`TabContainer`で[ステータス(HP/状態/担当セクション名の要約＋スキル訓練)][担当(セクション割り当てTree・割り当て/ログ/予測ボタン・完全踏破後の設定)]の2タブに分け、常時2カラムで詰め込んでいた旧UIより縦横それぞれを広く使えるようにした(担当セクションのTreeが余裕のある高さを持てるようになった)。マップのNPCアイコンをクリックした場合は一覧を経由せず直接そのNPCの詳細ビューを開く(`_open_npc_panel(show_detail)`)。詳細ビューの「← 一覧へ戻る」ボタンで一覧ビューに戻れる。

成長方法は以下の両輪:
- **経験値型**: 探索で該当スキルを使うことで自然に上昇する。知覚（発見試行のたびに）だけでなく、知恵・鍵開け・破壊（ゲート挑戦のたびに、成否を問わず）・戦闘力（戦闘の実ラウンド数分）も同様に、使うたびに経験値が入る。**資金を使わなくても、時間をかけて挑戦し続ければいつかは育つ**（5.2節の「試行回数がものを言う」思想を全スキルに適用。無課金プレイでも詰まりきらない）
- **資金ブースト**: 利益を使って明示的に訓練し、成長を加速できる。訓練コストは**現在のスキルレベルが高いほど高額になる**（一般的なインクリメンタルゲームの成長カーブ。次の一歩が徐々に重くなる）

### 4.4 雇用フロー

「雇う」＝募集をかける操作。募集をかけると、能力・先天的特性の異なる候補が複数人提示され、プレイヤーが選んで雇用する（ガチャ的な選択感）。

**雇用コスト**は候補の質によって変動する。能力値が高い、あるいはレアな先天的特性を持つ候補ほど雇用コストが高額になる。プレイヤーは「安く平均的な人材」か「高くて優秀な人材」かを都度選べる。

募集の発行タイミングは**プレイヤーが任意のタイミングで自由に行える**（月次などの制限はない）。雇用上限とコストのみが実質的な制約となる。

**コスト構造**: 募集を掛ける行為自体にコストが発生する（候補を見るだけでも課金される）。気軽に何度も募集を乱発できないようにし、雇用の意思決定に重みを持たせる。

**名前の自動割り振り(2026-09-13実装)**: 候補の名前は、8.1節と同じ「実行時にAPI生成しない」方針に合わせ、開発時にオフラインで用意した名前辞書(`name_generator.gd`)から抽選する。血筋（平民/旧家の血筋/森人の血/王家の落胤）ごとに雰囲気の異なる名前リストを持ち、候補生成時に決まった血筋に応じた名前を割り当てる。

### 4.5 雇用上限

同時に雇用できるNPC数には上限がある。上限は施設やプレイヤーのレベルによって拡張可能（成長カーブの一要素）。

施設拡張は、探索で得た利益と**同じ資金プール**を消費して行う（雇用・スキル強化・施設拡張が同じ資金を奪い合う3択のトレードオフになる）。

### 4.6 担当エリア

1人のプレイヤーが雇用する複数NPCは、同じマップを共有するのではなく、**NPCごとに担当セクションを分担**して探索する。並列探索により重複を避け、マップ全体を効率的にカバーできる。

**マップ上の表示(2026-09-13実装、同日中に表示位置を変更)**: どのNPCがどのセクションを担当しているか一目で分かるよう、NPCごとの小さなアイコン(現状は名前の頭文字のみ。将来的にはNPC個別の画像に差し替える想定)を表示する。クリックするとNPC管理パネルでそのNPCを選択した状態で開く。当初はセクション枠の見出し下にまとめて表示していたが、どのフロアで今動いているか分からないという指摘を受けフロア単位の表示に変更した(詳細は5.3節末尾)。

**割り当て候補の絞り込み(2026-09-13実装)**: 担当セクションの選択肢は、既に誰か(雇用/野良問わず)が到達しているか、隣接する突破済みノードから発見を試みられる状態(`WorldMap.is_section_reachable()`)のセクションだけに絞る。世界のどこからも繋がっていない未到達地帯を選んでも実際には何も進行しないため、そもそも選択肢に出さない(該当セクションが1つも無いエリアごと非表示になる)。

NPCを切り替えるたびに、担当セクションの選択肢(Tree)もそのNPCが現在割り当てられているセクションを選択済みの状態にする(以前選んでいたNPCの選択状態が残ったままにならないように)。

担当エリアの単位は**セクション（5.1のワールド階層）**とする。NPCは1つのセクションに割り当てられ、そのセクション内のフロアのみを探索する。1セクション＝1ダンジョン、あるいは1つの町周辺エリアのように、ノードグラフ上の意味のあるまとまりが担当割り当ての最小単位になる。

## 5. 探索

### 5.1 マップ構造

**ノードグラフ**（場所＝ノード、道＝エッジの接続関係の集合）。座標を持つ2Dグリッド/タイルマップではない。プレイ画面ではこのノードグラフを視覚的に表示する（ノード図・簡易マップ画面）。

**規模感**: 1ワールドあたり**中規模（数百ノード）**を目安とする。数ヶ月単位のプレイで少しずつ地図が埋まっていく規模感。

**ワールド階層（エリア／セクション／フロア）**: ワールドは3階層で構成する。
- **エリア**（国や地方など最上位区分）
- **セクション**（ダンジョンやフィールドなど、4.6の担当エリア割り当ての単位）
- **フロア**（ノードグラフ上の個々の場所。1つ1つが探索の最小単位）

セクションはマップ画面上でも視覚的に1つの枠として表示される（当初はGodotの`GraphFrame`機能を使っていたが、10章の通り素のControlノードによる自前描画に置き換え済み）。現時点では階層は表示・担当割り当て・掲示板の集約単位（7.1）としての意味を持ち、「セクション入場条件」のようなゲームルール上の追加制約は設けていない（個々のフロアのゲート条件はフロア単位のまま）。

**エリア間移動の支援(2026-09-13実装)**: マップが縦に長くなり、下の方のエリアまでスクロールするのが大変になったため、マップ上部にフロートで全エリア名のボタンを並べ、クリックするとそのエリアの先頭セクションの位置まで自動スクロールする機能を追加した。

**エリアの可視化(2026-09-13実装)**: セクション枠だけではエリア名がマップ上のどこにも表示されず、「小さな王国」がどこからどこまでを指すのか分からない問題があったため、所属セクション群を外接する大きな背景枠とエリア名の見出しを、セクション枠より背後に追加した。フロート表示のエリア選択バーがこの見出しの真上に重ならないよう、余白計算にバーの高さ分の余白(`MAP_NAV_BAR_CLEARANCE`)も加味している。

**フロア詳細のダブルクリック表示(2026-09-13実装)**: マップ上でフロアの箱をダブルクリックすると、そのフロア単体の詳細(所属セクション・状態・ゲート条件を人間可読にした説明・突破報酬アイテム・そのフロアに絞った行動ログ)をポップアップ表示する。フロアの箱に当たらなかった場合はセクション枠として扱い、そのセクションの掲示板スレッドを開く(NPC管理パネルの「このセクションのログを見る」ボタンと同じ処理を共有)。

### 5.2 発見（隠し通路）

- 指定スキルがないと進めない場所がある
- 行ける道や隠し通路に気づくかどうかは、探索中に**自動で判定される副次的な確率**（プレイヤーが明示的に「捜索しろ」と指示する必要はない）
- 知覚/発見スキルが高いほど気づく確率が上がる。特定パラメータ（先天的特性）を持つNPCのみ気づけるケースもある
- 前提条件を満たさないと進めない場所もある
- とにかく試行（日々の探索）を重ねることで開ける。十分な試行数がないまま終わる（何も気づかず終了する）こともある。回数がものを言う設計

**自動探索ループ（日次処理）**: 担当セクションに割り当てられたNPCは、1日ごとに以下を行う。
1. **ゲート再判定**: 「発見済みだが進めない」フロアについて、現在のスキル値/戦闘力でゲートを無音に再判定する（会話は開かない。突破できたらその場で「突破済み」に切り替わり掲示板に記録）
2. **発見試行**: 担当セクション内で、通過済みフロアに隣接する未発見フロア**全てに対して並列に1回ずつ**、知覚スキルに応じた確率で発見を試みる（隣接元は他セクションの通過済みフロアでもよい。例: ダンジョンの入口が村側からつながっている場合）

知覚スキルは発見を試みるたびに経験値を得て自然成長する（4.3節）。

### 5.3 障害・扉

見つけても、条件を満たさないと進めない。突破方法の例:
- リドル → 知恵が高くないと進めない
- 血筋 → 特定の血筋を持つNPCでないと開かない
- 特定アイテムの所持
- 鍵開け・破壊スキルによる突破

**アイテム所持ゲート**: 特定ノードを突破した際、発見者に固有アイテムが渡ることがある（`item_reward`）。そのアイテムを所持しているNPCだけが対応する`item`ゲートを通過できる。アイテムはNPC個人の所持品であり、パーティ共有ではない（例: ボスを倒したNPC自身が、そのすぐ先にある宝物庫を護符で開ける、という一本道の連鎖として機能する。現状は簡易的な「所持フラグ」のみで、アイテムの取引・売却・複数個所持などは未実装）

基本は**1NPC単位で完結**する設計（複数NPCの同時協力が必須になるギミックは現状想定しない。将来的な拡張候補ではある）。

ノードは3状態を取る: **未発見** → **発見済みだが進めない**（ゲート未突破。地図上に見えている）→ **突破済み**（先の探索が可能）。ゲートの通過/失敗は常にNPCのスキル値で自動判定され、7.3の会話ウィンドウは結果を決めるものではなく演出専用（特別にフラグを立てたノードのみ、初回発見時に一度だけ再生される）。これにより、通常のゲート判定では毎回会話が挟まらず、放置系としてのテンポを崩さない。

**マップ表示の色分け（2026-09-13〜）**: found/passed自体は7.1の通り世界共通のグローバル状態のままだが、マップ表示専用に「雇用NPC自身がそこへ到達済みか」（`found_by_employed`）を別途記録し、3色に塗り分ける。
- **自身**（雇用NPCが到達済み）: 明るい色＋ボーダー付き
- **誰か**（野良NPCのみが発見。雇用NPCはまだ未到達）: 通常色
- **未踏破**（誰も到達していない）: 暗い色、かつ名前を伏せて「????」と表示する（発見するまで実際の地名は分からない）

さらに「発見済みだが進めない」ノードは、上記3色のどれであっても半透明にし、突破待ちであることを一目で示す。雇用NPCが後から野良NPC発見済みの場所に到達（発見/突破）すれば、そのノードは自動的に「誰か」から「自身」へ切り替わる。プレイ開始地点（始まりの村/森の入口）は常に「自身」扱いとする。

**「誰か」から「自身」への切り替えバグ修正(2026-09-13)**: ゲートの無いフロアを野良NPCが先に発見・突破してしまうと`found=true`になった時点で、雇用NPCの日次処理(未発見フロアへの発見試行)の対象から永久に外れてしまい、担当の雇用NPCが実際にそのセクションで稼働していても「誰か」色から二度と「自身」色へ切り替わらない不具合があった(「ささやきの森」の入口フロアで発生を確認)。担当NPCが稼働中の日は、既に突破済みだが自分の踏破扱いになっていないフロアを合流させる処理(`Exploration._claim_wild_progress()`)を追加して修正。

**担当NPCアイコンの表示位置(2026-09-13変更)**: 当初はセクション枠の見出し下に、担当NPCの頭文字アイコンをセクション単位でまとめて表示していた。どのフロアで今動いているのか分からないという指摘を受け、フロア単位の表示に変更した(`_current_node_for_npc()`)。担当NPCはセクション内の未発見フロア全てに同時並行でアタックする実装のため厳密な「現在地」は存在しないが、表示上は(1)発見済みだが未突破のゲートがあればそこ、(2)無ければ既知の最前線(未発見フロアに隣接する突破済みノード)、(3)それも無ければ(完全攻略後など)セクション最後のノード、の優先順で代表フロアを決め、そのフロアの箱にアイコンを表示する。

**未到達セクションの明示(2026-09-13追加)**: `WorldMap.is_section_reachable()`がfalseのセクション(まだ誰も足を踏み入れておらず、隣接する突破済みノードも無い)には、セクション枠の下に「🔒 未到達」ラベルを表示する。ダブルクリックすると、他セクションから繋がる入り口ノードのうちまだ通れないものを列挙する詳細ウィンドウを開く(未発見の入り口ノードは名前を伏せる)。

### 5.4 戦闘

ボスや危険な生物との遭遇はHP・戦闘力パラメータを持つ戦闘として存在する（純粋なスキル判定・パズルではない）。

- 解決方式: 基本は自動（戦闘力の比較で進行）。プレイヤーの介入は**事前設定型の方針**として行う。戦闘発生の都度リアルタイムで選択を迫られることはなく、放置系としての一貫性を保つ
  - **発動条件**: HP割合のみ（例: 「HPが30%以下になったら発動」）。シンプルな1種類のしきい値に絞る
  - **発動後のアクション**: (1) アイテム使用（回復・逆転アイテムなど）、(2) 撤退判断（深追いせず自主的に退く）の2種類をNPCごとに事前設定できる
- 敗北時: 雇用NPCが永久に失われることはない（安全設計）。戦闘に敗れると**撤退して一時的に離脱**し、一定期間の回復待ちとなる。時間的なリスク・コストとして機能する
- 回復期間が明けるとHPは全回復し、探索を再開する
- **マップ上の扱い**: 戦闘はゲートの一種（`gate.type == "combat"`）として実装されており、5.3のスキル系ゲートと同じ枠組みで自動探索ループに組み込まれている。「アイテム使用」方針は根気強く戦い続ければ理論上いつか勝てる安全策、「撤退判断」は早めに損切りして再挑戦の機会を待つ方針、という役割の違いがある

## 6. 経済

### 6.1 収入(ワーカー配置型、2026-09-13実装)

資金の獲得経路は当初「探索で得た利益」とだけ構想されていたが、具体的な収入源が長らく未実装だった。以下の**ワーカー配置型**(スタークラフター系インクリメンタルゲームの資源ノード配置に近い)で実装済み:

- **月次収入**: 月末の集計タイムに、担当NPCが**現在いる**セクションごとに「そのセクションの累計突破フロア数 × セクション倍率」を資金として得る。配置転換すると元のセクションからの収入は失われる(常駐が前提)
- **セクション倍率**: セクションが所属するエリアの登場順(1始まり)がそのまま倍率になる。後発エリアほど高倍率になり、8.1節の「後発エリアほど規模と難度を緩やかに引き上げる」方針と自然に噛み合う。セクションごとに新規データを追加する必要はなく、エリアを追加するだけで自動的に反映される(`WorldMap.section_multiplier()`)
- **攻略報酬**: セクション内の全フロアを突破(完全攻略)した瞬間に一時金が入る(基礎額×セクション倍率×フロア数)。同一プレイで**本当に最初に**完全攻略したセクションだけ、追加の固定ボーナスが乗る(早期の足がかりを作るための一度きりの後押し)
- **踏破後の挙動設定**: 完全攻略したセクションの担当NPCは、NPCごとの設定(`Npcs.PostClearBehavior`)に従い「そのまま留まって収入源として維持する(STAY)」か「次の未踏破セクションへ自動的に配置転換される(MOVE_ON、デフォルト)」かを選べる。次のセクションは同じエリア内の未完了セクションを優先し、無ければ次のエリア以降から探す(`WorldMap.next_section_to_explore()`)
- **配置予測(2026-09-13追加)**: NPC管理パネルの担当セクション選択で「予測」ボタンを押すと、実際には配置転換せずに今月(30日)の見込みだけを計算して表示する(`Exploration.forecast_section()`)。セクション内の未突破フロアを、現在到達済みの場所から辿れる順に「発見にかかる予想日数」(1/発見確率を経路に沿って積み上げたもの)で並べ、月内に到達しうる範囲でNPCが実際に負ける(撤退/敗北になる)戦闘ゲートが無いかを、実際のHP/経験値には触れない非破壊シミュレーション(`Combat.predict_result()`)で調べる。見つかった場合、その戦闘に月内に行き着く確率分だけ予測報酬を割り引いて表示する(撤退が先に来れば、その分の報酬は無いものとして扱う期待値化)。スキル/所持品/血筋のゲートで現状塞がれている先はこの見積もりに含めない(今月中に抜けられる保証が無いため)

探索で得た利益（アイテム・資金）は、単一の資金プールとして扱い、プレイヤーが毎回配分を選べる:
- **拡大**: 募集コスト＋雇用コストを払って新規NPCを雇用する
- **強化**: 既存NPCのスキル訓練（資金ブースト）
- **拡張**: 施設に投資して雇用上限を引き上げる

3つの用途が同じ資金を奪い合うため、「今すぐ人数を増やすか」「今いるNPCを鍛えるか」「将来のために上限を広げるか」というトレードオフがプレイヤーの意思決定の中心になる。

**バランス方針**: 全体的に**テンポ良く拡大できる低フリクション**を志向する。序盤から次の雇用・強化にすぐ手が届く状態を保ち、「常に資金不足で悩む」重さは避ける。

**現在の実装値（初期チューニング。今後プレイテストで調整）**:

| 項目 | 数式・値 | 例 |
|---|---|---|
| 開始資金 | 300 | - |
| 募集コスト | 固定50 | - |
| 雇用コスト | 50 + 質(0〜1)×400 | 平均的人材50〜150、レア人材400〜450 |
| 訓練コスト | 20 × 1.4^現在レベル | Lv0→1: 20、Lv5→6: 107、Lv9→10: 413 |
| 施設拡張コスト | 300 × 1.6^拡張回数 | 1回目300、2回目480、3回目768 |

初回雇用は「募集50＋雇用50〜」で最低100（開始資金300の1/3）に収まるよう調整し、最初の一手を軽くしている。一方で施設拡張の初回コスト（300）は開始資金と同額とし、**施設拡張は中盤以降の目標**として意図的に重くしてある（序盤は雇用・訓練に資金を回す設計）。

## 7. 掲示板・イベント

### 7.1 内部掲示板

**常設ログ**。プレイヤーはいつでも過去の発見・成果を見返せる。集計タイムでは、その期間分の要約が表示される。

雇用NPCの発見だけでなく、野良NPCによる発見も**世界共通の情報**として掲示板に反映される（雇用NPCは「自分の利益のためだけの存在」ではなく、世界全体の探索状況の一部を担う）。

**スレッド化**: フロア単位の発見は頻繁に起きるため、全体フィードには載せず、**所属セクションごとのスレッド**にのみ記録する（プレイヤーはセクションを選んで詳細ログを閲覧できる）。全体フィードには、以下の**節目のみ**を掲載する:
- セクションへの初到達（世界で最初にそのセクションの何らかのフロアが見つかった瞬間）
- エリアへの初到達
- 7.3のイベント（ボス発見など）

これにより、野良NPCの日常的な発見が全体フィードを埋め尽くし、プレイヤー自身のNPCの成果が埋もれる、という問題を避けている。野良NPCも雇用NPCと同じ実データを探索するため、同じフロアが「誰かに先に見つかられて二重に報告される」ことは起きない（世界全体で1つのfound/passed状態を共有する）。

**UI（2026-09-13〜）**: 掲示板は他の機能（雇用/NPC管理/行動ログ/セーブ）と同じく、サイドバーのボタンから開くウィンドウに統合されている。全文・スレッド切替はそのウィンドウ内で行う。ボタン直下には全体フィードの直近10件だけを常時表示する小さなプレビュー欄があり、ウィンドウを開かなくても最新の動きをざっと確認できる。

### 7.2 イベント

ボスや遺跡の発見など。世界から隠されており、条件が整うと発見され、発見後は誰でも認識できるようになる。

表示タイミングはイベントの**重要度・規模で事前分類**される:
- 重要度が高い（ボス発見など世界規模の重大事）→ 即時表示
- 重要度が低い（小規模な発見）→ 月次集計にまとめて表示

### 7.3 イベント会話ウィンドウ

特定条件を満たしたイベント（ボス戦、障害突破、発見イベントなど）は、専用の会話ウィンドウを開いて演出する。ボス戦や謎解きだけでなく、幅広いイベントで共用する汎用の仕組みとする。

- **UI**: 画面下部に固定表示。左右にキャラクター（現段階では名前プレート＋色付き四角のプレースホルダ）、中央に発言者名とセリフ、必要に応じて選択肢ボタンを表示するオーソドックスなノベルゲーム形式
- **時間の扱い**: 会話が開いている間はゲーム内時間を一時停止し、閉じるまで次の進行は起きない
- **進行方式**: 選択肢付き分岐に対応する。プレイヤーの選択によって結果（例: 謎解き成功/失敗、戦闘継続/撤退など）が変わる
- **データ形式**: 会話は「行」の配列で表現する。各行は話者・セリフに加えて、次の行番号（省略時は+1）、選択肢（ラベルと分岐先）、または会話を終了させる`outcome`（結果コード）を持つ。会話システム自体は結果コードを返すだけで、それをどう扱うか（ゲートを開ける、戦闘結果を反映する等）は呼び出し元の各システムが決める疎結合な設計

## 8. ワールド生成・永続化

### 8.1 生成

マップ・アイテム・障害の内容は、**開発時にClaude Codeを使ってオフライン生成**し、DBに格納する。ゲーム実行中にAPIを呼び出してリアルタイム生成することはしない（APIコスト・レイテンシの問題を回避）。

この規模のデータを扱うため、SQL（DB）での管理が必要。

**現状の実装**: コンテンツ定義はUI（`main.gd`）から分離し、`world_data.gd`という専用のオートロードに集約している（起動時にWorldMapへ流し込むだけの役割）。**コンテンツの正本は引き続き`world_data.gd`のGDScriptコード**（`add_area`/`add_section`/`add_node`/`set_event_scripts`の読みやすい呼び出しのまま、今後もこの形で書き足していく）で、`world_schema_db.gd`が起動のたびにその内容をSQLiteファイル（`user://worldseeker_world_schema.sqlite`、8.2節参照）へスナップショット出力する。DBは「実行時に生成される派生キャッシュ」という位置づけで、DBの行を直接手で編集する運用は想定していない。ノードグラフの画面表示位置は手動指定をやめ、セクションごとのグリッド自動レイアウトに変更済み（ノード数が数百規模に増えてもセクション同士が重ならない）。

現在のワールド内容は**9エリア・39セクション・194フロア**規模まで拡張済み。王国「小さな王国」＝村周辺/古い洞窟/ささやきの森/国境の道/王都/貴族街の6セクション、隣国「レインヴェール」＝郊外/沈んだ遺跡/隠れ森の郷/遺跡の深層の4セクション、隣々国「灰色の山嶺」（レインヴェール郊外の古い物見塔から接続）＝峠道/ドワーフの砦/廃坑/竜の尖塔の4セクション、「忘れられた地下墓地」（王国・貴族街の大聖堂の鐘楼から接続）＝納骨堂入口/白骨の回廊/沈黙の礼拝堂/リッチの聖域の4セクション、「精霊界」（レインヴェール・隠れ森の郷の精霊の祠から接続）＝狭間の境界/漂う島々/鏡影の窪地/星幽の聖域の4セクション、「月魄の湖」（レインヴェール・隠れ森の郷の月の泉の守護者から接続。精霊界とは別の行き止まりから分岐）＝湖畔/沈んだ里/葦の迷路/月宮の4セクション、「妖精の隠れ里」（王国・ささやきの森の古井戸から接続。ゲート無しの行き止まりが起点）＝隠れ里の入口/茸の群生地/悪戯妖精の迷路/妖精の宮廷の4セクション、「結晶の深淵」（灰色の山嶺・廃坑の結晶洞から接続）＝結晶への降下路/晶洞の窪み/共鳴の回廊/結晶の玉座の4セクション、「業火の火口」（灰色の山嶺・竜の尖塔の灰塵の間から接続。9エリア目にして初めて5セクション構成に拡大）＝火口の縁/黒曜石の平原/燠火の坑道/溶鉱の鍛冶場/業火の中心の5セクション。ゲートは知恵（最大Lv5）・鍵開け（最大Lv4）・破壊（最大Lv3）・知覚（最大Lv4）・戦闘（最大敵戦闘力120、業火の王で更新）・血筋（先天的特性、4種のうち3種を使用済み: 王家の落胤/旧家の血筋/森人の血）の全種類を、複数の難易度段階で使用している。アイテムゲートは20系統（ゴブリンの護符/古い探検隊の地図/盗賊の印章/深淵の王冠/ドワーフの鍛冶槌/坑道主の鍵/灰塵の竜鱗/銀の聖遺物匣/砕けたフィラクテリーの欠片/星の欠片/星幽の核/月の真珠/月魄の冠/妖精の粉塵/女王の寵愛の証/共鳴する欠片/結晶の心臓/黒曜石の欠片/業火で鍛えた鋼塊/業火の心臓の計20アイテム）あり、うち1つ（盗賊の印章）は王都で入手し貴族街で使う**セクションをまたいだ**報酬チェーン、残り19個は同一セクション内で完結するチェーン。イベント会話は83箇所に設置。全ゲート種別・複数セクションをまたいだ探索（同一NPCの担当セクション再割り当てを含む）・アイテム報酬チェーンまでシミュレーションで動作確認済み。「数百ノード」目標に対してはまだ規模が小さく、追加のコンテンツ肉付けは今後も継続課題。

**方針（2026-09-12決定）**: 後発エリアほど規模と難度を緩やかに引き上げていく。目安としてセクション数4→5、ノード数19前後→28前後、戦闘ゲートの敵戦闘力上限110→120程度（9エリア目の「業火の火口」で実際に5セクション・28ノード・敵戦闘力120まで適用済み）。過去エリアの遡及的な作り直しは行わず、以降の新規エリアから適用する。敵の強さ自体は依然として`world_data.gd`上でノードごとに手書きする値であり（8.1節の方針通りコンテンツは正本コード直書き）、エリア内では入口から遠いノードほど`enemy_power`を高く設定する、という執筆時の慣習であって、深さから自動算出するランタイム機構ではない。

### 8.2 保存・リプレイ

「一度使ったワールドの設定を保存し、リプレイ用に使う」とは、以下の両方を指す:
1. **記録再生**: 特定プレイ回の行動ログを保存し、後から観戦・再生できる
2. **スキーマ再プレイ**: 生成済みのワールド構造（ノードグラフ・ギミック配置など）はテンプレートとして保存し、新しいNPCや別プレイヤーが同じマップにゼロから再挑戦できる

**現状の実装（進行状態の保存/復元）**: `save_system.gd`が`addons/godot-sqlite`(GDExtension、Windows x86_64バイナリのみをリポジトリに同梱)経由でSQLiteファイル(`user://worldseeker_save.sqlite`)に進行状態を保存/復元する。保存対象は資金・雇用NPC名簿(血筋/スキル経験値/所持品込み)・ワールドの発見/突破状態・掲示板ログ(全体+スレッド)。テーブルは`meta`(スカラー値のキーバリュー)・`npcs`/`npc_traits`/`npc_skills`/`npc_inventory`(NPC関連を正規化、JSON blobは使わない)・`world_progress`・`board_entries`/`board_threads`/`board_thread_entries`・`action_log`(後述)の10個。`meta`以下`board_thread_entries`までは保存のたびに全テーブルをDELETEしてから現在の状態を丸ごと再INSERTする(差分更新はしない)。日次(`TimeSystem.day_advanced`)およびウィンドウを閉じたタイミングで自動保存し、起動時に自動ロードする。あわせて「セーブスロット」パネルに「今すぐセーブする」(手動セーブ、2026-09-13追加)ボタンもあり、オートセーブを待たずに任意のタイミングで明示的に保存できる(分岐前のチェックポイントを作りたい、という要望への対応)。同パネルの「オートセーブを有効にする」チェックボックス(2026-09-13追加、`SaveSystem.autosave_enabled`、`worldseeker_meta.cfg`に永続化)でオートセーブ自体をオフにもできる。オフの間も手動セーブ・進行の複製・新規プレイ開始・スロット切替/削除など、プレイヤーが明示的に行う保存(`SaveSystem.save_game()`を直接呼ぶ経路)は影響を受けない(`SaveSystem.autosave()`という専用の入り口だけがこのフラグを見る)。多NPC・複数セクションをまたいだ状態(血筋/所持品/スキル値を含む)での保存→ロード一致をシミュレーションで確認済み。

**現状の実装（記録再生＝行動ログ）**: `action_log.gd`が担当。採用方式は**ログビューアー方式**（決定論的リプレイ＝乱数のシード管理をして同じ結果を再現する方式ではない）。粒度は掲示板と同じ「意味のある出来事のみ」（発見・ゲート突破・マイルストーン。日々のゲート再挑戦の失敗などルーチン判定は記録しない）で、`exploration.gd`の掲示板投稿と同じ箇所から構造化された行を追加で記録する。掲示板の`text`が表示用の整形済み文字列だけを持つのに対し、`action_log`テーブルは`day`/`event_type`/`npc_id`/`node_id`/`section_id`という構造化列を持ち、後から特定NPCやノードで絞り込める。他テーブルと異なり**削除されない追記専用ログ**で、`ActionLog`がメモリ上にバッファした新規分だけを保存のたびにINSERTする。プレイ回をまたいでも区別できるよう`run_id`を発行し、`meta`テーブル経由でセーブ/ロードされる。閲覧用ビューアーUIは`main.gd`の専用パネル（「行動ログを見る」ボタン）として実装済みで、NPCで絞り込める（`SaveSystem.query_action_log()`がその場でDBに問い合わせる。常時メモリに保持はしない）。

**現状の実装（分岐用のスロット複製、2026-09-13追加）**: 「新規プレイを開始する」(`SaveSystem.create_new_slot()`)は進行をゼロから作り直すため、今の進行を保ったまま別の道を試したい(分岐前のチェックポイントを残したい)場合の手段が無かった。`SaveSystem.duplicate_current_slot()`を追加し、セーブスロットパネルの「現在の進行を複製する」ボタンから、今のスロットのファイルをそのまま新しい空きスロットIDへコピーするだけの複製を行えるようにした(WorldMap/Npcs等の再構築は不要で、複製前に`save_game()`で最新状態をディスクへ反映してからファイルコピーする)。複製後もアクティブスロットは元のままなので、複製先は後から「このスロットを開く」で好きなタイミングで辿れる、もう1本のセーブとして残る。

**現状の実装（スキーマ再プレイ＝複数セーブスロット＋ワールドスキーマの複数バージョン管理）**: 8.1節の`world_schema_db.gd`によるワールドスキーマのDB出力（`_write_snapshot()`）に加え、そこからWorldMap/Itemsを再構築する`import_into_worldmap(version_id)`を実装した。`world_data.gd`の`add_area`/`add_section`/`add_node`/`set_event_scripts`呼び出し経路と全く同じWorldMapの公開メソッドを通るため、GDScript直書き経路とDB経由の経路は常に同じ形のWorldMapに収束する。どのノードが「最初から突破済み」（village/forest_edgeなどのスタート地点）かはスキーマDBの`nodes.initially_passed`列に記録し、`world_schema_db.gd`の`_ready()`が`WorldData._ready()`の直後・`SaveSystem.load_game()`より前に実行される（project.godotのautoload順）ことを利用して、実プレイの進行状態と混ざらない「まっさらな初期状態」だけを捉えている。

**複数バージョン管理**: WorldMap/Itemsの内容を正規化したJSONのSHA-256を`schema_version`とし、`user://schemas/schema_<version_id>.sqlite`にバージョンごとの別ファイルとして保存する（内容アドレス方式。同じ内容なら同じハッシュ=同じファイルなので、実際に内容が変わった時だけ新しいファイルが増える）。各セーブスロットは保存のたびに自分が実際に読み込んでいる`WorldSchemaDb.active_version_id`を`meta.schema_version`へ記録する。起動時（`main.gd`の`_ready()`冒頭、UIを組み立てる`_seed_demo_world()`より前）に、アクティブなスロットの`schema_version`が今の`world_data.gd`が生成するバージョン（`WorldSchemaDb.active_version_id`、起動直後は常に最新）と異なれば、そのスロット自身のバージョンで`import_into_worldmap()`し直す。`SaveSystem.switch_to_slot()`でスロットを切り替える際も同様に、そのスロット自身の`schema_version`（記録がなければ現行バージョンにフォールバック）で再構築する。**重要な注意点**: `WorldMap.add_area`/`add_section`/`add_node`と`Items.define`はどれも上書きのみで削除はしないため、`import_into_worldmap()`は必ず先に`WorldMap.reset()`/`Items.reset()`で完全にクリアしてから読み込む（これを怠ると、以前読み込んでいた別バージョンにしかない要素が残ってしまう不具合になる。実際にマルチバージョン切替のシミュレーションでこの不具合を検出し、`reset()`を追加して修正した）。

セーブデータは`user://saves/slot_<id>.sqlite`としてスロットごとに分離し（テーブル定義は共通、パスだけが違う）、アクティブなスロットIDは`user://worldseeker_meta.cfg`で管理する。`SaveSystem.create_new_slot()`は新しいスロットを作り、Economy/TimeSystem/Npcs/Recruitment/Board/ActionLogをそれぞれの`reset()`で初期化し、常に最新の`WorldSchemaDb.current_version_id`でワールドを再構築してから保存する。`SaveSystem.delete_slot()`でスロットを削除できる（アクティブな＝現在開いているスロットは切り替え先が定まらないため削除不可、ガードしている）。UIは`main.gd`の「セーブスロット...」パネル（スロット一覧・切替・削除・確認ダイアログ付きの新規プレイ開始ボタン。削除も確認ダイアログ経由）。バージョン管理自体にはUIを設けず、裏側で自動的に動作する。プロセス再起動を模した2バージョン間のシミュレーション（旧バージョンのスロットを継続 → 新バージョンで新規スロット作成 → 両スロットを行き来）で、それぞれが自分の生成時点のマップ形状（ノードの有無・`initially_passed`状態）を正しく保つことを確認済み。

## 9. マルチプレイ展望

## 10. 技術スタック

- **エンジン**: Godot 4.7（GDScript）。既存プロジェクト（MyCells）と同じ構成で、学習コストを抑える
- **配布形態**: Windowsネイティブ export（.exe）。まずはローカルで自分だけが遊ぶ想定（9章のマルチプレイ展望とは別に、配布はローカル前提から始める）
- **マップ描画**: 当初はGodot標準の`GraphEdit`/`GraphNode`/`GraphFrame`を流用していたが、ノード・フレームをドラッグで動かせてしまいプレイ中に意図せずレイアウトが崩れる問題があったため、素の`Control`(`Panel`/`PanelContainer`/`Label`、`mouse_filter = IGNORE`でそもそもドラッグ処理を持たせない)による自前描画に置き換えた。ノード間の接続線は`draw_line()`で自前描画。`GraphEdit`はノードグラフ**編集**用のウィジェットであり、読み取り専用のマップ表示には使うべきでないという判断。ScrollContainerだけでは数百ノード規模を動き回りづらいため、キャンバスの空き領域を左ドラッグしてパンできる機能を独自実装で追加した（GraphEditのパン操作の代替）。マウスホイールでのズームも追加済み（2026-09-13〜）: `Control.scale`はScrollContainerがスクロール範囲を正しく再計算してくれないため使わず、ズーム倍率に応じてセル/ノードサイズなどのレイアウト定数を計算し直してマップ全体を再構築する方式にした。カーソル直下のコンテンツ座標がズーム後も同じ画面位置に留まるよう、スクロール位置も再計算する
- **UIテーマ(2026-09-13実装)**: Godotの既定テーマのままだと、押せる/選択できる要素(Button/Tree/ItemList)と、ただの文字(Label)との見た目の力差が乏しく、選択・押下してもわずかにしか色が変わらないという指摘があった。個々のControlごとにスタイルを都度指定するのではなく、`main.gd`の`_build_theme()`でButton/OptionButton/Tree/ItemListの通常/ホバー/押下・選択中/無効の各状態にはっきり彩度差のあるStyleBoxFlatを設定した`Theme`を1つ作り、ルートのControlに設定して以降add_childする全パネル・全ボタンに伝播させている(個々のボタン生成箇所を1つずつ直す必要がない)。押下中/選択中は彩度の高い青にはっきり変える方針
- **永続化**: `GDSQLite`アドオン（`godot/addons/godot-sqlite`、Windows向けバイナリのみ同梱）を2つの用途に使い分けている。(1) `save_system.gd`: セーブデータ（進行状態: 資金・NPC・ワールド探索進捗・掲示板ログ・行動ログ）を`user://saves/slot_<id>.sqlite`に複数セーブスロットとして保存（8.2節）。(2) `world_schema_db.gd`: `world_data.gd`が構築したワールドスキーマを、内容のSHA-256をバージョンIDとして`user://schemas/schema_<version_id>.sqlite`へバージョンごとに保存し、各セーブスロットは自分が生成された時点のバージョンを`meta.schema_version`に記録して、継続/切替のたびにそのバージョンでWorldMapを再構築する（8.1/8.2節）。用途が異なるため意図的に別ファイルに分けている
- **プロジェクト構成**: `godot/` 以下にGodotプロジェクトを配置。主要システムはautoloadシングルトンとして分割（`time_system.gd` / `world_map.gd` / `items.gd` / `world_data.gd` / `world_schema_db.gd` / `npcs.gd` / `wild_npcs.gd` / `recruitment.gd` / `economy.gd` / `board.gd` / `action_log.gd` / `combat.gd` / `event_dialogue.gd` / `exploration.gd` / `save_system.gd`）。スキル種別は `skill_types.gd`（`class_name SkillTypes`）で共有定義。NPCの名前辞書は`name_generator.gd`（`class_name NameGenerator`、血筋ごとの事前生成リスト）で共有定義。`world_data.gd`はコンテンツ定義専用で、UIコード（`main.gd`）から独立している。`items.gd`はアイテム定義とNPC所持品を管理する最小限のシステム
- **自動探索ループ検証済み**: NPCの雇用→担当セクション割り当て→日次の発見/ゲート突破（スキル・戦闘）→イベント会話の自動発火→掲示板記録までの一連の流れを、シミュレーションで動作確認済み
- **初期スキャフォールド検証済み**: `scenes/main.tscn` + `scripts/main.gd` で、募集→候補提示→雇用、ノードグラフのマップ表示、掲示板ログ表示までの最小ループが実際に動作することをGodotエディタでの起動確認済み
