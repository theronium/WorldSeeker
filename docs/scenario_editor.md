# シナリオ・イベントエディタ 設計(2026-09-21)

世界の中身(マップ・イベント会話・画像の割り当て)を「シナリオ」としてデータ化し、ゲーム本体とは別の**ブラウザのエディタ**で編集できるようにする。設計の経緯は、ユーザーとの2回の質疑(範囲・起動条件・画像・ゲーム側・条件の種類・効果・編集UI・保存形式)で決めた。

## 用語

| 用語 | 意味 |
|---|---|
| シナリオ | キャラ(話者)・NPC・敵の画像割り当て、イベント、マップを一纏めにしたもの。フォルダ1つ |
| イベント | シナリオ内の1つの会話(導入、戦闘、謎解きなど)。発生条件・会話の台本・終了時の効果を持つ |
| デフォルト(default) | リポジトリに含めて公開するシナリオ。`godot/scenarios/<id>/` |
| カスタム(custom) | 個人用で公開しないシナリオ。`user://scenarios/<id>/`(Windowsでは`%APPDATA%\Godot\app_userdata\WorldSeeker\scenarios\<id>\`)。リポジトリには入らない |

## 範囲(決定事項)

- **世界全体をデータ化**する。`world_data.gd`(GDScript直書き)は廃止し、エリア/セクション/フロア/ゲート/アイテムを`world.json`に、会話をイベントのJSONに移す。ゲームはシナリオから世界を組み立てる。
- **エディタで編集できるのは、会話・イベント・画像の割り当て、マップ**(マップの編集は、初版の次の段階として同日中に追加した。下の「マップの編集」)。
- 画像は、既存ライブラリ(`godot/assets/portraits/`の`npc_*`/`enemy_*`/`char_*`)から選ぶのに加えて、**シナリオ固有のPNGをアップロード**できる。
- ゲーム側は、**新規開始時にシナリオを選び、セーブに紐づける**。

## フォルダ構成

```
scenarios/<id>/
  scenario.json     基本情報(id・名前・説明・作者・開始年月)
  world.json        マップ(アイテム・エリア・セクション・フロア)
  cast.json         登場人物(話者名→画像)
  events/<event_id>.json   イベント1本=1ファイル
  images/*.png      シナリオ固有の画像
```

Gitで差分が読めるよう、JSONは整形(インデント2、キー順固定)して書く。

### scenario.json
```json
{"format": 1, "id": "default", "name": "小さな王国", "description": "…", "author": "", "start_year": 0, "start_month": 1}
```

### world.json
順序が意味を持つ(エリアの並び=難度倍率、セクションの並び=退避先の判定)ため、全て配列。
```json
{
  "items":    [{"id": "goblin_amulet", "name": "ゴブリンキングの護符"}],
  "areas":    [{"id": "kingdom", "name": "小さな王国"}],
  "sections": [{"id": "old_cave_dungeon", "name": "古い洞窟", "area": "kingdom"}],
  "nodes":    [{"id": "cave", "name": "洞窟", "section": "old_cave_dungeon", "connections": ["forest_edge", "locked_vault"],
                "gate": {"type": "skill", "skill": "LOCKPICKING", "min_level": 2}, "item_reward": "", "initially_passed": false}]
}
```
ゲート: `skill`(`skill`はSkillTypes.Skillの名前)/`combat`(`enemy_power`)/`item`(`item`)/`innate_trait`(`trait`,`value`)。ゲート無しは`{}`。

### cast.json
```json
[{"name": "案内人", "image": "npc_01", "side": "left"}]
```
画像idは、ライブラリのid(`npc_01`など)か、シナリオ固有画像の`@ファイル名.png`。`side`は、エディタが新しい行を作る時の既定の左右(`left`/`right`)。会話の行に`image`キーがあれば、その行だけ画像を上書きする。表に無い話者は、従来どおり名前のハッシュで自動選択される。

### イベント(events/*.json)
```json
{
  "id": "floor_old_shrine_pass",
  "title": "古い祠(突破)",
  "trigger": {"type": "gate", "floor": "old_shrine", "result": "pass"},
  "conditions": [],
  "repeat": false,
  "priority": 0,
  "kind": "auto",
  "script": [ {"side": "none", "name": "古い祠", "text": "…", "next": 1}, {"side": "none", "name": "", "text": "…", "outcome": "pass"} ],
  "effects": [ {"on": "pass", "type": "set_flag", "flag": "shrine_opened", "value": true} ]
}
```

**トリガー(`trigger.type`)**
- `gate`: フロアのゲート結果。`floor`と`result`(`pass`/`fail`)。探索者がフロアを発見した時、ゲートの結果に合う方が再生される(従来の突破用/失敗用の2本組と同じ)。台本の終わりの`outcome`は`pass`/`fail`にすること(ゲームがこれで突破を確定する)。
- `conditions`: `conditions`の全てが成り立った日に、1度だけ発生する(`repeat: true`なら、成り立っている間は毎日。フラグを降ろす効果と組み合わせて止める)。毎日の探索の最後に判定し、1日に再生するのは、優先度(`priority`)が最も高い(同じならid順の)1本だけ(会話が既に開いていれば、他のイベントは翌日へ持ち越す)。
- `system`: ゲームの決まった場面(案内会話)で、コードから呼ばれる。`name`は`intro_part1`(起動直後と、新規プレイの開始直後。**シナリオごとに一度だけ**。「見た」記録はシナリオ別で、デフォルトは従来のキーを使う)/`intro_part2`(初めての割り当て直後)/`party_formed`(初めての雇用直後)/`retreat`(初めての撤退)。**ユーザーが選んだ条件の種類には無かったが、導入や撤退の説明会話をシナリオ側へ移すために必要なので足した**。

**条件(`conditions[]`、全てAND)**
- `{"type": "day_min", "day": 30}` — 経過日数がN以上
- `{"type": "flag", "flag": "名前", "value": true}` — フラグが立っている(`false`なら立っていない)
- `{"type": "floor_found", "floor": "id"}` / `{"type": "floor_passed", "floor": "id"}`
- `{"type": "section_entered", "section": "id"}` / `{"type": "area_entered", "area": "id"}`

**効果(`effects[]`)**: 会話が終わった時、その`outcome`が`on`と一致する(`"*"`なら全て)ものを順に適用する。
- `{"type": "set_flag", "flag": "名前", "value": true|false}`
- `{"type": "funds", "amount": 100}`(負なら支出。資金は0未満にならない)
- `{"type": "grant_item", "item": "id"}`(そのアイテムをまだ持たない雇用探索者のうち、名簿の先頭の1人へ渡す)
- `{"type": "open_floor", "floor": "id"}`(そのフロアを突破済みにする)

選択肢の結果でフラグを分けたい時は、選択肢ごとに別の`outcome`コード(`help`/`refuse`など)で終わらせ、効果の`on`で分ける。

**種別(`kind`)**: `auto`(フロアのゲートの種類から自動=従来どおり)/`""`(種別なし)/`boss`/`combat`/`skill`/`item`/`bloodline`/`guide`。

## セーブとの関係

会話の中身は**セーブスロットごとに、世界のスナップショット(world_schema_db.gd、内容ハッシュで版管理)に含める**。スナップショットにはワールドに加えて、シナリオ情報・イベント・登場人物表を入れる。よってスロットは、後でシナリオを編集・削除しても、遊び始めた時点の内容で再開できる(画像ファイルだけは外部参照なので、無ければ自動選択の画像に戻る)。

スロットに追加で保存するのは、フラグ(`scenario_flags`)と、発生済みイベント(`scenario_events_fired`)。旧セーブ(この機能より前)のスナップショットには`events`表が無いので、読み込み時にフロアの突破用/失敗用の台本から`gate`イベントを起こし、登場人物表はデフォルトシナリオのものを使う。

## エディタ(`tools/scenario-editor/`)

Node.js製の**依存パッケージなしのローカルサーバー**(`node server.js`)+ ブラウザのページ。ブラウザ単体では、ディスク上のフォルダを自由に読み書きできないため、サーバーがシナリオのフォルダと画像を扱う。

機能: シナリオの一覧・新規作成(デフォルト/カスタムを選ぶ)・複製・削除・読み込み / イベントの追加・編集・削除・検索(エリア/セクション/フロアで絞り込み)/ 会話の行の追加・修正・削除・並べ替え(行リストで編集、分岐先はプルダウン、脇に簡易フロー図)/ 話者の画像の選択とアップロード / 発生条件・効果の編集 / **会話のリプレイ**(ゲーム本体と同じ見た目で再生。選択肢も選べる)/ 検証(行き先の範囲・存在しないフロアやフラグの参照など)/ **マップの編集**(次節)。

## マップの編集(2026-09-21)

ユーザーとの質疑で、範囲は「フロアの追加・削除・名前・所属セクション」「接続とゲート」「セクション・エリアの追加・並べ替え」「アイテム定義と報酬」の全て、画面は「表・ツリー形式」に決めた。画面は「マップ」タブ: 左に エリア>セクション>フロア のツリー(名前・IDで絞り込み、エラー/警告の印)と「アイテム定義」、右に選んだものの編集フォーム。上のバーの「マップを保存」(Ctrl+S)で`world.json`を書く。編集は「下書き」に対して行い、保存するまで「元に戻す」で全て取り消せる(イベントの編集とは独立)。

**並びが意味を持つ**(ゲーム側の使われ方。フォームにも注記してある):
- **エリアの並び**=収入・報酬の倍率(N番目=×N。`WorldMap.section_multiplier`)と、「先へ進む」で動く時の順序。
- **エリア内のセクションの並び**=マップ画面での上からの並びと、勝てない敵から退避する時の退避先の判定(並びで前にある攻略済みのセクション。`WorldMap.previous_cleared_section`)。
- **セクション内のフロアの並び**=ゲームのマップ画面での配置(左上から右へ、5個(`MAP_COLUMNS`)ずつ折り返し。`main.gd`の`_compute_node_positions`)。ゲームは座標を持たない。セクションのフォームに、この配置をそのまま格子で出す。
- 並べ替えは、隣の兄弟と入れ替える(▲▼/◀▶)。別のセクション・エリアへ移すと、移した先の最後に入る。ファイルでは、同じ親の要素が隣り合うように挿入する(ゲームは親で絞り込むので、間に別の要素が挟まっても動くが、読みやすさのため)。

**接続は常に双方向で保存する**: ゲームは、発見されるフロア**自身の**接続に、突破済みの隣があるかで発見できるかを決める(`WorldMap.frontier_for_section`)。片方にしか書かれていない接続は一方通行になるので、エディタは追加・削除とも双方に書く。手で書いた片方向の接続は、検証が警告し、フロアの接続欄の「そろえる」で直せる。

**IDの変更は、参照ごと付け替える**: フロア・セクション・エリア・アイテムのIDを変えると、世界の中の参照(他のフロアの接続、フロアのセクション、セクションのエリア、ゲートのアイテム、突破報酬)は下書きの時点で付け替わる。**保存済みのイベントの参照**(`trigger.floor`、条件の`floor`/`section`/`area`、効果の`open_floor`/`grant_item`)は、保存の時に付け替えて、書き換えたイベントも同じ要求で保存する(各要素が持つ`_orig`=保存済みのときのIDから、「旧ID→新ID」を求める。入れ替わり(AとBを交換)も同時に正しく付け替わる)。保存していないイベントの編集があり、かつ付け替えるイベントがある時は、先にイベントを保存(破棄)するよう促して止める。

**削除は、参照するイベントを消さない**: フロアの削除は、他のフロアからの接続も外す。セクション・エリアの削除は、中のフロア(セクション)ごと消す。それらを参照している保存済みのイベントは、削除の確認に一覧を出すが、消さずに残す(保存後の検証で「存在しません」のエラーになるので、イベントタブで直す)。条件を勝手に消すと発生の意味が変わってしまうため。

**検証**(`worldlogic.js`の`validateWorld`。マップタブの印・「概要・問題」・上のバーの全体の検証に出る):
- 保存を**止める**(`fatal`)もの: IDの形式違反・重複、存在しないセクション/エリアへの所属、存在しないフロアへの接続・自己接続、ゲートの種類・技能名が不正(ゲームが読み込めなくなる)。
- 警告・エラー(保存はできる): 片方向の接続、開始地点(`initially_passed`)が無い、開始地点から接続をたどっても発見できないフロア(イベントの効果「フロアを開放」の対象は出発点に数える)、戦闘力・レベルが1以上の整数でない、ゲートや報酬のアイテムが未定義、ゲートに要るアイテムを入手する手段(どこかの報酬・イベントの効果)が無い、フロアの無いセクション・セクションの無いエリア、名前が空。

**サーバー**: `PUT /api/scenarios/:source/:id/world`(本体`{world, events}`)。`world`は形(型・ID・重複)だけを検査して書く(意味の検証はエディタとゲームの読み込み)。`events`は、IDの付け替えで書き換えたイベント(**既存のものだけ**。新しく作れない)。イベントを先に、`world.json`を最後に書く(途中で失敗しても、同じ内容でやり直せる)。

**書式**: `world.json`は`worldlogic.js`の`canonicalWorld`が、ゲームが書く形・キー順(ゲートは種類ごとに固定)にそろえる。デフォルトの`world.json`を、エディタが読んで書き直しても1バイトも変わらない(テストで確認済み)。

**ゲームでの確認**: `tools/dev/sim_map_edit.gd`(手順はそのファイルの冒頭)。エディタのロジックで編集(エリア・セクション・フロアの追加、ID変更、並べ替え、移動、削除、4種のゲート、アイテム定義)したシナリオを、ゲーム本体が読み、並び・接続・ゲート・アイテム・イベントが期待どおりで、追加したフロアを実際に発見でき、セーブ往復まで通ることを確認する。

## スマホへの持ち込み(2026-09-21)

カスタムシナリオはPCの`user://scenarios/`にあるので、そのままではスマホで遊べない。ユーザーとの質疑で、次のように決めた: **経路はzipファイル+ゲーム内の取り込みボタン**(ケーブル経由の「スマホへ送る」ボタンにはしない。ケーブルが無くても運べる)/ 追加機能は**スマホ上のカスタムシナリオの一覧・削除**と**エディタでのzip取り込み**(ゲームからのzip書き出し=スマホ→PCは選ばなかった)/ 同じIDが既にある時は**確認して上書き** / zipは**1シナリオ1ファイル**。

**流れ**: エディタの「zip書き出し」(`worldseeker_scenario_<id>.zip`。ディスクに保存済みの内容が入る)→ ファイルをスマホへ(USB転送・`adb push`など。**この端末のファイル選択にはGoogleドライブが並ばない**ので、端末内に置く)→ ゲームのセーブ/ロード画面の「シナリオを取り込む」でファイルを選ぶ → 内容の確認 → 「シナリオ:」の一覧に出る → 「新規プレイを開始する」で遊ぶ。

**zipの中身**: `manifest.json`(`{"format": "worldseeker-scenario", "version": 1, "id", "name", "exported_at"}`。形式の印で、セーブのファイル(`worldseeker-saves`)を間違えて選んだ時に、分かる理由を出せる)と、シナリオのフォルダの中身そのまま(`scenario.json` / `world.json` / `cast.json` / `events/<id>.json` / `images/<名前>.png`)。圧縮はdeflate(画像は無圧縮)、ファイル名はUTF-8。デフォルトシナリオ(9エリア・170イベント)で約100KB。

**取り込みの検査**(エディタ`server.js`の`parseScenarioZip`と、ゲーム`scenario_transfer.gd`は、同じ規則。外から来るファイルなので厳しめ):
- ファイル名は信用せず、上の決まった形の名前だけを拾う(`../`や余計なファイルは無視。何個無視したかは、取り込み結果に出る)。
- 大きさ: 1ファイル4MB(JSONは2MB)・合計64MB・1500ファイル・zip本体48MBまで。**申告された展開後の大きさで先に判断する**(展開爆弾の対策。ゲーム側の`ZIPReader`は申告の大きさで先にメモリを確保するので、中央ディレクトリを自前で読んで、読む前に弾く)。CRC・展開後の大きさの一致も確かめる(エディタ側)。暗号化・zip64は非対応。
- 中身: `manifest.json`の形式と版、`scenario.json`のID(`^[a-z][a-z0-9_]{1,40}$`)と名前、`world.json`(ID・名前・所属・重複、**ゲートの種類ごとのキーと技能名**=不正だとゲームが読み込み時にエラーになる)、`cast.json`の形、イベント(ファイル名とIDの一致、発生のしかた、会話の形、**条件・効果の種類ごとの必須キーと型**)、画像がPNGか。エディタの「保存を止める」検証(fatal)と同じ考え方で、**ゲームが存在を前提に読むもの**を確かめる。意味の検証(存在しないフロアへの参照など)は、取り込みでは行わない(エディタの検証の役目)。

**エディタ**: 上のバーの「zip書き出し」(`GET /api/scenarios/:source/:id/export`。保存していない変更があると、含まれない旨を確認する)と「zip取り込み」(ファイル選択→取り込み先(カスタム/デフォルト)→`POST /api/scenarios/import?source=…&overwrite=1`)。同じIDがある時はサーバーが409(`{exists, id, name}`)を返し、画面が上書きの確認を出す。標準のシナリオ(`default/default`)は上書きできない。書き込みは一時フォルダに完成させてから入れ替える(途中で失敗しても、元のシナリオが壊れない)。zipの読み書きは`tools/scenario-editor/zip.js`(依存なし、Node.jsのzlibだけ)。

**ゲーム**(`scenario_transfer.gd`の`ScenarioTransfer`。autoloadを参照しないので、`--script`の確認から名前で呼べる): セーブ/ロード画面の「シナリオを取り込む」→ OSのファイル選択(`_show_file_dialog`)→ `read_import_file()`で検査して一時フォルダ(`user://import_scenario_tmp`)へ展開 → 確認画面(名前・ID・フロア/イベント/画像の数・作者・説明。同じIDがあれば「上書きします」と、ボタンが「上書きして取り込む」)→ `install_import()`で`user://scenarios/<id>/`へ(既にあれば退避→入れ替え→失敗なら復元)。「シナリオの管理」は、一覧(`list_custom()`)→選んで「選んだシナリオを削除」→確認→`delete_custom()`→一覧を開き直す。削除時に、案内会話の「見た」記録も消す(`SaveSystem.forget_scenario_records()`)。**遊び始めているセーブは、上書き・削除しても、遊び始めた時点の内容のまま**(スナップショット。会話の画像だけは外部参照)。詳細は design.md 8.2節。

## 実装メモ(形式の細部)

- 行の`next`を省略すると、次の行(i+1)へ進む。ゲームのデータは全ての行に`next: i+1`を明示してあるが、同じ意味。エディタは、行の挿入・削除・移動の前に、この明示を省略へ直す(並びを変えても「一覧の並び=会話の流れ」になるように)。
- 終わり(`outcome`)に達すると会話が終わる。範囲外の`next`も、結果コード無し(`""`)で終わる。フロアの会話(`gate`)は`pass`/`fail`で終わる必要がある(ゲームは、この結果コードでフロアの突破を確定する。エディタが検証する)。
- イベントは、フロアの会話(`gate`)を含め、`ScenarioEvents.play()`で再生する。終了時に発生済みへ記録し、効果を適用する。フロアの会話は、フロアの突破の確定(`Exploration._finalize_discovery`)の後に効果が働く。
- 画像idの`@ファイル名.png`は、そのシナリオの`images/`のPNG。デフォルトシナリオのものは`res://`(エクスポートで取り込まれる)、カスタムは`user://`(実行時に読む)。
- JSONの整形は、ゲーム(`ScenarioStore.write_json`)もエディタ(`JSON.stringify(x, null, 2)`)も同じ(インデント2、キーは入れた順、末尾に改行)。キー順は`logic.js`の`canonicalEvent`が固定する。デフォルトの全イベントを、エディタが読んで書き直しても、1バイトも変わらない(テストで確認済み)。
